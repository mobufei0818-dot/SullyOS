一、这份文件解决什么问题
------------------------

本文件只记录“角色在聊天结束后，如何在合适时间重新主动联系用户”的完整逻辑。

SullyOS 目前有两套互相配合、但绝不能混为一谈的机制：

1. 原版主动消息 2.0（AMSG 2.0）
   - 角色或用户创建定时任务。
   - 到点后由已部署的 Cloudflare Worker 调用聊天模型，读取最新聊天上下文，生成一条真实聊天消息。
   - 任务可手动创建、角色通过工具自行创建、取消、续期、查询。

2. 关系主动消息层（2026-08-31 新增）
   - 不替代 AMSG 2.0，也不另建一套发消息后端。
   - 在角色正常回复后，自动建立一条“未来联系机会”。
   - 若角色说过有现实后续的话，例如“开完会来找你”“到家告诉你”，优先按合理的现实时间窗安排。
   - 用户再次发消息时，自动撤销这条旧的关系层任务，再根据新聊天重新计算。
   - 到点后的最终措辞仍由原版 AMSG 2.0 Worker 读取最新上下文决定；前端不会伪造角色消息。

二、已有主动消息 2.0 的原版逻辑
------------------------------

原版主动消息 2.0 的关键路径：

- 聊天模型在对话中可选择调用 schedule_active_message 工具。
- 工具生成一条主动消息任务，存入当前角色的 activeMsg2Config.tasks。
- 前端在创建前上传该角色当前的 fire pack（角色卡、聊天上下文、世界书、日程、工具配置等）到 Worker。
- Worker 到点执行任务时，使用当时最新可用的 fire pack 和 API 凭据生成消息。
- Worker 发送后，消息进入正常聊天记录；它不是普通浏览器定时器，因此用户关闭网页后也可以执行。

重要事实：

- 原版模型“是否调用排程工具”是可选的。角色说“忙完来找你”并不代表模型一定自行创建任务。
- 这就是之前出现“角色承诺了，但后来没有主动找你”的根因。
- 关系主动消息层的目的正是补上这一层遗漏，但不会取消角色原本自己创建的任务。

三、当前 Worker 与部署信息
--------------------------

用户现有主动消息 2.0 Worker：
https://sullyos-amsg.mobufei-0818.workers.dev/

用户已按原版教程部署该 Worker。关系层复用此 Worker 的既有：

- 任务创建接口 schedule-message；
- 任务取消接口 cancel-message；
- D1 中的用户任务与凭据记录；
- Cron 定时触发；
- 原版 fire pack / 到点防穿帮判定 / 最新上下文生成流程。

本次关系层没有修改 Worker 代码，也没有要求用户再次填写 Worker 地址、共享密钥、AMSG_MASTER_KEY 或 API Key。

前提：

- 系统设置中原版主动消息 2.0 的 Worker 全局配置必须完成；
- 具体角色的主动消息 2.0 必须处于开启状态；
- 聊天 API URL、Key、Model 必须可用；若角色设置了主动消息专用副 API，也仍沿用原版规则。

四、关系主动消息层的数据结构
------------------------------

角色资料 CharacterProfile 新增两个可选字段：

1. relationshipProactiveConfig
   每个角色独立保存的关系层设置。

   enabled
   - 是否开启关系主动消息层。
   - 默认关闭，避免未明确启用的角色自行增加联系任务。

   initiativeStyle
   - reserved：克制。
   - natural：自然（默认）。
   - clingy：黏人。
   - 影响没有明确承诺时的联系间隔，以及承诺跟进的时间倾向。

   quietHoursEnabled / quietHoursStart / quietHoursEnd
   - 免打扰开关与开始、结束时间。
   - 按角色自己的时区判断；不使用设备时区替代异国角色的当地时间。
   - 默认 23:30 至 08:00。

   dailyLimit
   - 关系层每天最多创建多少个联系机会，范围 1 到 5，默认 2。
   - 只限制关系层；不限制用户手动创建或角色自行创建的原版任务。

   followUpPromises
   - 是否对“忙完 / 到家 / 结束后”等有现实后续含义的回复优先安排跟进。

   showHeartCard
   - 是否在最新角色文字消息末尾显示爱心入口。

2. relationshipPulse
   关系卡的本地只读快照，不直接强塞给模型表演。

   affection：好感度。
   jealousy：醋意值。
   baselineLonging：思念值基线。
   lastUserReplyAt：最后一次用户回复时间。
   innerVoice：心声，界面最多显示 30 个字符。

五、关系层如何安排时间
----------------------

1. 角色有明确现实后续

关系层不是看到一个固定关键词就强制发消息。它先粗略判断角色回复是否带有未完成的现实后续，再建立一个“到点时重新判断”的机会。

目前的合理中位时间：

- 会议、上课、汇报、工作等：约 70 分钟；
- 回家、路上、通勤等：约 45 分钟；
- 买东西、取快递、做饭、洗澡、办事等：约 40 分钟；
- 休息、午睡、补觉等：约 100 分钟；
- 其它明确“之后再联系”的表述：约 90 分钟。

不同主动程度会略微缩短或拉长这些时间。这个值只是“重新判断的时间窗口”，不是角色向用户承诺的精确闹钟。

2. 没有明确承诺

如果没有现实后续，关系层也只会保留一个较克制的未来联系机会：

- 黏人：约 3.5 小时为基础；
- 自然：约 5.5 小时为基础；
- 克制：约 8 小时为基础；
- 思念值越高，间隔会适度缩短，但不会缩到分钟级反复打扰。

3. 到点时的最终判断

创建的是 AMSG 2.0 的 prompted 一次性任务。提示方向要求角色：

- 结合自身设定、日程、最新聊天和真实经过的时间；
- 事件仍未结束、用户刚回复、或不适合打扰时，直接跳过；
- 不得提及“排程”“系统”“思念值”或“被要求来联系”；
- 只有自然且合理时才发送符合角色性格的一句话。

因此，前端不会把“会议预计 70 分钟”伪装成角色必定会在 70 分钟后说话。

六、任务创建、取消与防重复规则
--------------------------------

关系层任务在 activeMsg2Config.tasks 中使用：

source: 'relationship'

它与以下 source 明确区分：

- user：用户在主动消息 2.0 面板手动创建；
- character：角色通过 schedule_active_message 工具自行创建；
- relationship：关系层自动创建。

规则：

- 用户新增任意真实消息（手打、图片、小程序卡片等）后，关系层只取消 source=relationship 的任务；
- 不会误删 user 或 character 任务；
- 取消成功的任务才从本地清单移除；网络失败的任务保留，避免本地显示消失但云端仍会触发；
- 同一角色同一时间只允许一条待触发的关系层任务；
- 收到原版 AMSG 2.0 推送消息时，不会再由该消息反复安排下一条关系任务；
- 打开旧聊天不会为历史消息补排任务（只处理近 15 分钟内刚生成的正常角色回复）；
- 每日关系层任务数量存于浏览器 localStorage；私密模式或存储被清空时，只会失去该本地计数，不影响 Worker 本身。

七、原版防穿帮逻辑仍然有效
----------------------------

关系层任务使用 expire_policy: 'expire'。

原版主动消息 2.0 到点防穿帮规则会检查触发前后是否处于热聊：

- 如果用户正好在任务触发附近与角色聊天，任务可以作废；
- 如果角色从最新上下文发现事情已经被说完，也应跳过；
- 用户主动回复时，关系层又会提前远端取消任务。

这三层共同避免出现“用户刚回消息，角色又按旧话题跑来问一次”的情况。

八、关系卡 UI
--------------

位置：

- 只显示在当前聊天中最新一条角色文字消息的末尾；
- 点击小爱心“♥”打开关系卡；
- 不是额外插入一条聊天消息，也不传给模型。

卡片显示：

- 思念值；
- 好感度；
- 醋意值；
- TA 的心声（最多 30 字）。

心声优先取现有情绪系统最后一次生成的 innerState；没有时使用简短本地兜底文案。

数值会基于最近对话、用户回复间隔、互动数量和部分聊天语境实时重算；界面每分钟刷新一次，不额外调用 API。

九、设置入口与使用步骤
----------------------

每个角色分别设置：

1. 打开该角色聊天；
2. 点击输入框左侧“＋”；
3. 打开“聊天设置”；
4. 找到粉色的“关系主动消息”区域；
5. 开启“关系主动消息”；
6. 选择主动程度、每日上限、免打扰、承诺跟进、爱心卡；
7. 同时确认该角色原本的“主动消息 2.0”已开启。

建议初始值：

- 主动程度：自然；
- 每日最多：2 次；
- 免打扰：23:30 到 08:00；
- 承诺后自然跟进：开启；
- 爱心卡：开启。

十、与原版更新的兼容策略
--------------------------

关系层刻意复用而不是替换原版能力：

- 任务仍走 ActiveMsgClient.scheduleCharacterTask；
- 取消仍走 ActiveMsgClient.cancelTask；
- 任务仍落在 activeMsg2Config.tasks；
- 最终消息仍由原版 Worker / fire pack / AMSG 2.0 收件流程处理。

以后同步原版时：

1. 先查看 upstream 主动消息 2.0 是否修改了任务类型、任务 payload、ActiveMsgClient、fire pack 或 Worker API；
2. 合并原版更新；
3. 确认 source='relationship' 不被原版的 source 枚举、筛选、UI 文案或任务清理逻辑遗漏；
4. 确认 scheduleCharacterTask / cancelTask 的参数与返回值仍兼容；
5. 构建并测试：角色回复 → 任务出现；用户回复 → 只撤销关系层任务；到点后 Worker 消息正常入聊天；
6. 若原版 Worker bundle 更新，需要同时按自己的 Cloudflare 部署方式部署 Worker；网页 GitHub Pages 更新不会自动改已部署的 Worker。

十三、与朋友圈阶段 4 Worker 的挂载边界（2026-09-01）
------------------------------------------------------

本专题前文记录的是关系主动消息层本身；朋友圈阶段 4 后续新增的 Worker 路由已按以下方式接入，
不会改变本专题所述的 AMSG 任务链路：

- 上游原版 `qegj567-cloud/SullyOS` 当前没有 `worker/moments` 或 `/moments` 路由；原版仓库只读，未被修改。
- 用户 fork 仅在 `worker/amsg/src/index.ts` 增加一个 fork-only wrapper：`/moments/*` 交给
  `worker/moments/src/index.ts`，其余路径仍按上游 AMSG handler 处理，`scheduled()` 与原版任务流程不变。
- 朋友圈和关系层复用同一 Cloudflare Worker、同一 `DB` binding 与现有 `AMSG_SERVER_TOKEN`（请求头为
  `X-Client-Token`），不新建第二个 Worker、D1、URL 或共享密钥。朋友圈设置从主动消息 2.0 全局配置只读读取这些值。
- 正式替换的部署文件是合并后的 `worker/amsg/worker.bundle.js`。`worker/moments/worker.bundle.js` 仅作独立
  模块预览/测试，不能覆盖用户正在运行的 AMSG bundle。
- 后续原版 Worker 更新必须先比较 `worker/amsg` 的上游差异，再重新确认这个 `/moments/*` wrapper、token
  fallback 和路由前缀仍在；构建后仍只升级现有 AMSG Worker。网页 Pages 发布不会自动升级 Cloudflare Worker。


十四、原版 AMSG outbox 清理的 D1 免费额度修复（2026-09-02）
------------------------------------------------------------

1. 本次确实改动了二改 fork 中的原版 AMSG Worker 公共路径，位于
   `worker/amsg/src/index.ts`。没有向 `qegj567-cloud/SullyOS` 原版远程写入任何内容；而是在用户 fork
   内包装上游 AMSG 的 D1 adapter 和 `scheduled()`。它不是朋友圈独立模块的修复。
2. 根因：上游默认在每分钟 Cron 中都执行两条 `message_outbox` 保留期清理。同一批行被每日
   重复扫描 1440 次，实测单日 D1 rows read 约 900 万，超过免费层 500 万限额，导致数据库、
   设备登记和更新后的自动验证一起报错。
3. 保留的修复规则：
   - `* * * * *` 每分钟定时触发器和到点任务检查保持不变，不影响主动消息准时性；
   - 仅 `message_outbox` 清理改为每个 UTC 整点执行一次（每小时一次）；
   - 已确认消息保留 7 天、未确认消息保留 28 天的上游语义不变；
   - 为 `message_outbox(acked_at)` 补部分索引 `idx_outbox_acked_cleanup`；
   - 为 `message_outbox(created_at)` 补索引 `idx_outbox_created_cleanup`；
   - 索引在 `initSchema` 后幂等创建，老数据库在额度恢复后点一次“重新连接并验证”即会补齐。
4. 以后合并原版时，本节是不可静默回退的二改保留项。冲突时不得直接选上游 `theirs`，必须复核：
   - `createD1Adapter` 包装和 `OUTBOX_CLEANUP_INDEX_SQL` 仍在；
   - `shouldRunHourlyOutboxCleanup` 仍以 Cron 的 `scheduledTime` 判断 UTC 整点；
   - `buildWorkerConfig` 仍向上游注入包装后的 db；
   - `scheduled()` 仍只在本次触发上下文中传递时间，并在 `finally` 恢复；
   - 每分钟任务拾取、关系 tick、朋友圈离线任务仍正常，只有 outbox 保留期清理是小时级。
   如果上游以后重写了 outbox 清理接口，应迁移“低频率 + 可用索引 + 保留期不变”的语义，不能为了
   保留旧实现而阻止上游更正确的新方案，但也绝不能回到每分钟全表扫描。
5. 源码修复提交：`958dc399`；Worker 版本标记为
   `2026-09-02.d1-cleanup-1`，补标提交：`9550f1f0`。之前显示 9.1 只是版本常量漏递增，不代表清理修复没有进入 bundle。
