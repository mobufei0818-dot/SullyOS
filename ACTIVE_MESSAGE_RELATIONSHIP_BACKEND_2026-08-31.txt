一、本次目的
------------

原版主动消息 2.0 中，角色是否主动创建定时任务由模型自行决定。因此角色说“开完会来找你”或
“到家告诉你”时，模型可能没有实际排程，之后就不会回来联系用户。

本次新增“关系主动消息层”，让角色关系状态可以在网页关闭时仍由 Cloudflare Worker + D1
持续计算。在合适时机，它只创建一条原版 AMSG 2.0 任务；最终生成、推送、聊天写入、取消和
防穿帮继续使用原版流程。它不是另一套聊天系统，也不直接伪造消息。

二、架构和边界
--------------

1. 原版 AMSG 2.0 负责：
   - 定时任务、聊天模型调用、最新 fire pack/聊天上下文读取；
   - 推送、收件箱、聊天落库、任务取消和到点热聊防穿帮；
   - 使用角色既有的聊天 API 凭据。

2. 新增关系层只负责：
   - 保存每个角色的思念值、下一阈值、当天送达数、pending 任务、好感度、醋意和心声；
   - 在后台推进思念值；
   - 满足阈值、承诺跟进或每日目标时，调用原版加密 `schedule-message` 创建 prompted 任务；
   - 原版 fire 结束后回写“已送达/跳过/失败”，解除 pending 锁。

3. 隐私：
   - 前端同步角色 ID、时区、配置、最后互动时间、好感/醋意/心声摘要、用户互动方向；
   - 不把完整聊天正文或 API Key 再存一份给关系层；
   - D1 中整份关系状态 payload 用现有 AMSG_MASTER_KEY 派生的用户密钥加密。

三、思念值规则
--------------

- 首次开启不是固定从 0 开始：网页按当前角色人设、记忆和最近聊天给出合理初始估值。
- 基础第一阈值固定为 30。
- 粘人：约 +5/10 分钟；从 0 到 30 约 1 小时。
- 自然：约 +1.5/10 分钟；从 0 到 30 约 3 小时 20 分。
- 克制：约 +1/10 分钟；从 0 到 30 约 5 小时。
- 用户回复不会把思念值清零：普通互动略降；亲密表达可小涨；关系不会因高频聊天永久没有机会主动联系。
- 派发一次任务后思念值不归零，下一阈值至少增加 30 点，防止短时间连发。

四、频率与防打扰
----------------

- `dailyLimit = 0` 是“无限”：只按阈值。
- 其它数值是“每日主动消息目标”，不是硬上限；系统只在自然空档尝试补足，不打断热聊。
- 默认最短自然间隔 60 分钟，最低保护 30 分钟。
- 免打扰按角色时区计算，默认 23:30–08:00。
- 一个角色存在 pending 关系任务时不创建第二条。
- 原版 Worker 最终若判定热聊、事件已结束或不宜打扰而跳过，关系层会解除 pending，未来仍可自然计算。

五、承诺后跟进
--------------

开启“承诺后的自然跟进”后，角色刚说出有现实后续含义的回复，网页只同步类别与到期时间：

- 会议、上课、工作、汇报：约 70 分钟；
- 回家、通勤、路上：约 45 分钟；
- 买东西、取快递、做饭、洗澡、办事：约 40 分钟；
- 休息、午睡、补觉：约 100 分钟；
- 其它“晚点/之后再联系”：约 90 分钟。

粘人略短、克制略长。时间到了只代表“给角色一次自然联系机会”；仍要经过免打扰、最短间隔、
pending 保护和原版 fire-time 最新上下文判断，绝不是死板闹钟。

六、D1 性能优化（本次重要修改）
------------------------------

原版 Cron 必须每分钟运行，关系层不能每分钟把所有角色状态读一遍。

本次在 `sully_relationship_state` 加 `next_tick_at` 和索引：

- 开启角色约每 10 分钟才读取、解密、计算并写回一次；
- 关闭角色约 24 小时后才检查一次；
- Cron 只取 `next_tick_at <= 当前时间` 的行；
- 不再全表读取并逐行反查 user ID。

一般个人用量约为每角色 144 次关系结算/天，远低于免费层日常可承受范围。不要删除 D1 或
修改 AMSG_MASTER_KEY，否则历史主动消息和加密状态可能无法解密。

七、前端 UI
------------

入口：角色聊天 → 输入框左侧“＋” → 聊天设置 → 关系主动消息。

可设置：开关、克制/自然/粘人、每日目标（含无限）、免打扰、承诺跟进、关系卡展示。

关系卡改为点击角色消息旁头像的小爱心打开，不再塞在消息末尾；显示思念值、下一阈值、好感度、
醋意、当天已送达数、心声。心声默认折叠，可展开，不再强截 30 字。

十三、已实施：关系入口、剧情外卖事件与思念值回落（2026-08-31）
--------------------------------------------------------------

本节三项均已在 2026-08-31 实现并构建验证。外卖 App 本体维持空置；这里的“外卖”
仅指聊天角色扮演中明确说出已经给对方点了/下单了外卖的后续事件。

1. 关系卡入口视觉简化
   - 删除角色头像上叠加的小爱心图标及任何额外装饰。
   - 直接点击角色发送消息旁的角色头像，即可打开关系卡。
   - 保留关系卡本身的思念值、好感度、醋意值、心声等只读展示。

2. 剧情外卖与关系主动消息联动
   - 用户或角色在聊天中明确表示已给对方点了/下单了外卖，即建立一次明确后续事件；
     “想吃”“帮我点一下”等尚未下单的意愿句不会触发。
   - 默认送达窗口为该消息发出后 25–35 分钟，以消息自身稳定计算，重复同步不会改变 ETA。
   - 角色给用户点单：到达前后由 Worker 创建一次原版 AMSG 联系机会，角色自然询问用户
     “外卖收到了吗 / 下楼拿了吗”等。
   - 用户给角色点单：到达前后由 Worker 创建一次原版 AMSG 联系机会，角色自然告诉用户
     “我拿到了 / 刚取到外卖了”等。
   - 两种情况都由 Worker 创建原版 AMSG 联系机会，不直接伪造消息；仍受免打扰、热聊防穿帮、
     最短间隔与每日目标保护。即使通用“承诺后跟进”开关关闭，明确外卖事件仍可进入关系层。
   - 不再把“骑手到了下楼拿了拍给你”按泛用“等会/之后联系”处理。

3. 思念值回落规则优化
   - 不再对每一条新用户消息固定回落 4 点；热聊时这样会让数值下降过快。
   - 按“重新连接间隔”决定回落：很久未联系后的第一条用户回复明显回落（约 -6 至 -10），
     但不清零；间隔 20–60 分钟的小幅回落（约 -1 至 -2）；连续热聊时每条最多约 -0.2 至 -0.5，
     也可以不回落。
   - 亲密表达可抵消回落或小幅上涨，不应一律按普通回复处理。
   - Worker 内部应保存小数，关系卡仍展示取整值；始终限制最低为 0，不出现负数。
   - 当前实现的分档为：间隔至少 3 小时约 -8；至少 1 小时约 -4；20–60 分钟约 -1.5；
     少于 20 分钟的热聊每条约 -0.35。亲密表达额外 +2、疏离表达额外 +1，均与回落合并计算。
   - Worker 内部保存小数，关系卡展示四舍五入后的整数；下限始终为 0。

十五、排程延后修复与诊断口（2026-08-31）
---------------------------------------------

问题定位：关系卡显示“思念值已超过下一阈值”不等于原版 AMSG 任务已经创建。创建前仍会受
等待下一轮 Worker 检查、pending 锁、最短间隔、免打扰和创建接口失败影响。旧实现另有一处
真实 bug：聊天页每分钟同步关系状态时，都会把 D1 的 `next_tick_at` 重置为“当前时刻 + 10 分钟”；
只要页面持续打开，就可能持续推迟关系层检查。

本次修复：

1. Worker 保存关系状态时会保留仍在未来的、更早的 `next_tick_at`；前端同步不会再把已排好的
   检查向后推迟。已到期的检查在 Cron 处理后才正常安排下一轮。
2. 新增只读“排程诊断”入口：在角色头像打开的关系卡内点击“排程诊断 → 查看”即可看到：
   - `pendingTaskUuid`：是否有一条已创建但尚未由原版 AMSG 结算的关系任务；
   - `lastDispatchAt`：最近一次成功创建关系任务的时间；
   - `next_tick_at`：关系 Worker 预计进行下一次检查的时间；
   - “任务创建失败”：上一次调用原版任务创建接口失败时的安全摘要与时间；
   - “当前状态”：Worker 根据上述值计算出的明确阻塞原因。
   诊断不返回聊天正文、角色提示词、API Key、地址或其他私密数据。
3. 诊断判读：若思念值超过阈值但“下一次阈值”仍未提高，表示任务尚未成功创建；任务一经创建，
   Worker 会立即把阈值提高至少 30 点。若创建后用户又继续聊天，原版 fire-time 防穿帮可跳过
   消息，但那是后续阶段，和“仍显示旧阈值”是两件事。
4. 本次网页构建与 GitHub Pages 发布已通过。Worker bundle 也已更新；用户必须在 Cloudflare
   Dashboard 用最新版 bundle 替换并 Deploy，诊断和修复才会在运行中 Worker 生效。

十六、第二层 Cron 节流缺陷与最终修复（2026-08-31）
------------------------------------------------

用户实测发现第一轮修复后 `next_tick_at` 仍会从较早时间不断推到较晚时间。诊断截图显示：
阈值已达到、没有 `pendingTaskUuid`、最短间隔已过、没有任务创建失败，但 `next_tick_at`
仍在前端同步后后移。根因如下：

1. `lastCalculatedAt` 原本同时承担两个职责：
   - 每次同步/检查后用于累计思念值的时间锚点；
   - Cron 判断“是否距上一次关系检查满 10 分钟”的节流锚点。
2. 聊天页每分钟同步会推进 `lastCalculatedAt`；Cron 因而每分钟都误判“尚未满 10 分钟”而跳过。
   当旧 `next_tick_at` 已过期后，下一次同步又重新排“当前 + 10 分钟”，造成时间持续后移。

最终修复：

- 新增 `lastTickAt`，仅在 Worker Cron 实际完成一轮关系检查时更新；`lastCalculatedAt` 只保留
  思念值计算职责，前端同步不再影响 Cron 节流。
- 当思念值已达到阈值，且没有 pending、最短间隔或免打扰阻塞时，保存状态会将
  `next_tick_at` 安排到下一分钟 Cron，而不是十分钟后。
- 仍保留十分钟节流：一次真实检查完成后，下一轮正常关系检查才在十分钟后进行；不会因网页
  保持打开而无限后推，也不会无意义地每分钟重复创建任务。
- 排程诊断新增 `lastTickAt`，用于区分“前端刚同步”与“Worker Cron 真正检查过”。

本次源码已构建通过并发布到 GitHub Pages；运行中的 Cloudflare Worker 仍需替换为本次最新 bundle
并 Deploy 后才具备该最终修复。

十七、关系数值手动校正（2026-08-31）
---------------------------------------

为处理排程故障期间思念值持续增长而偏高的情况，新增关系卡内的“手动校正”入口：

1. 在角色头像打开的关系卡中，展开“手动校正”，可输入“思念值”和“下一阈值”。
2. 两项均只能保存 0–100；Worker 内部同样强制限制，不能通过前端绕过。
3. 点击“保存到后端”后，网页向 `/relationship/state` 发送带 `manual` 字段的同步请求，
   Worker/D1 加密关系账本直接写入校正值。不是只改卡片显示，刷新、退出页面或下次 Cron
   都会从已校正的后端数值继续计算。
4. 修复前已经超过 100 的旧阈值，会在下一次同步或 Cron 检查中收敛到 100；任务成功创建后
   的“下一阈值 +30”也同样封顶为 100。
5. 若把下一阈值设得不高于当前思念值，且没有 pending、最短间隔或免打扰阻塞，Worker 会在
   下一次 Cron 尝试创建原版主动消息任务。

十八、主动消息发送后的情绪释放与阈值闭环（2026-08-31）
------------------------------------------------------

审查原有阈值逻辑后确认，旧代码在“原版任务创建成功”时就提高下一阈值；若任务随后因热聊
跳过或生成失败，会出现阈值已提高、角色却未实际联系的矛盾。本节为最终规则：

1. 达到阈值时，只创建一条带 `pendingTaskUuid` 的原版 AMSG 任务；不在此刻扣思念值，也不提高阈值。
2. 只有原版 fire-time 回执确认 `sent` 且确有消息送达时，才视为角色完成一次主动联系：
   - 粘人角色思念值回落 6 点；
   - 自然角色回落 8 点；
   - 克制角色回落 10 点；
   所有值仍限制在 0–100。
3. 发送成功后，以回落后的实时思念值重设下一阈值：
   `nextThreshold = min(100, longingAfterRelief + 30)`。
   例如发送前为 30 / 阈值 30，发后回落为 20，则下一阈值为 50；不再沿旧阈值直接累加。
4. 若任务被热聊跳过、失败或取消：只清除 pending 锁；不回落思念值、不提高阈值、不增加每日发送数，
   也不更新“上一次成功主动联系”的最短间隔时间。
5. `lastDispatchAt` 的语义改为最近一次真正送达的关系主动消息时间；任务刚排上不再占用最短间隔。
6. 每日上限现为统一硬限制：达到用户设置的次数后，无论是思念阈值、承诺跟进还是剧情外卖到点，
   都不再创建关系主动消息。每日次数未满时，原有“在自然空档补足目标”的逻辑仍有效；设为
   无限（0）时则只受阈值、承诺、最短间隔与免打扰规则约束。

二十、云端生成偶发长时间无结果：只读检查记录（2026-09-01）
----------------------------------------------------------

用户现象：环境和网络设置没有主动变化，但角色的云端回复偶尔会持续生成很久，过一段时间又自行恢复。
本节只记录已经核实的链路和下次取证方法；本次没有修改网页、Worker、D1、Cloudflare 配置或部署。

1. 已确认存在 Worker 入口链路抖动
   - 维护端连续直连 `https://sullyos-amsg.mobufei-0818.workers.dev/config-check` 时，多次在 TLS
     握手完成前收到 `connection reset by peer`，HTTP 状态为 000，没有响应头和正文。
   - macOS 系统解析器能返回 Cloudflare 地址，但原始 DNS 查询结果曾与系统解析器不一致；说明同一设备上也可能
     存在 DNS、代理节点、运营商路由或缓存层的波动。用户不需要手动切换 Wi-Fi/代理，这些中间链路也可能自行变化。
   - 这种失败发生在 Worker 业务代码执行前。对应请求通常不会出现在 Worker fetch 日志里；不能把它误判成
     D1、Cron、模型提示词或情绪评估错误。

2. 请求已经进入 Worker 后，源码允许长时间等待与退避重试
   - `/instant-chat` 先保存任务并返回 202，再由每条任务独立的 `InstantTickDO` alarm 执行；不同任务不共用
     一个全局生成锁。alarm 起跳失败时，每分钟 Cron 仍可兜底拾取任务。
   - 即时对话单次 fire 总时长上限为 600000ms（10 分钟）；单个 MCP 调用最多 25 秒，整轮 MCP 总预算
     最多 120 秒。
   - 模型调用或工具链失败后，上游按约 2、4、6 分钟退避重试，最多重试三次。模型服务临时超时、429、
     5xx 或 Cloudflare 到模型供应商之间的连接抖动，都可能表现为“持续生成数分钟甚至更久，随后恢复”。
   - 前端只要点名查询仍得到 pending，就不会凭等待时长擅自判死；可见页面每 60 秒查询一次，页面回到前台
     会立即续查。因此长时间显示“云端生成中”不等于每分钟重复调用一次模型。

3. 已排除的误判
   - `[emotion-eval] 评估失败 ... AbortError` 不是主回复失败。情绪副 API 最多运行 120 秒，但主回复只顺带
     等 10 秒；没赶上时回复先发，评估结果随后补写或本轮放弃。
   - 当前源码没有发现会让所有角色周期性一起锁死的全局任务锁；每条即时任务使用独立 Durable Object。
   - 仅凭“后来自己好了”不能断言是 Worker、用户网络或模型供应商中的哪一层，必须对齐同一任务的时间与日志。

4. 下次复现时需要保留的证据（不要提供 Key、Token、完整提示词或聊天正文）
   - 发生时间（精确到分钟）、角色名或 charId、界面上能看到的任务 UUID；若有“停止生成”或失败提示，连同
     原文截图保存。
   - 浏览器网络日志：请求 URL 路径、HTTP 状态、耗时、是否收到响应头/字节，以及错误是 `Load failed`、
     `connection reset`、`AbortError` 还是明确的 4xx/5xx。
   - Cloudflare 同一时间段日志，重点搜索：`[amsg:instant-tick]`、`LLM_CALL_FAILED`、
     `AGENTIC_TOTAL_TIMEOUT`、429、502、503、`failedTasks`、`retryCount`、`nextRetryAt`、
     “叫醒 DO 失败（等 cron 兜底）”。
   - 若只有前端零字节/握手失败且 Cloudflare 没有对应 fetch：判为设备到 Worker 的入口链路问题。
   - 若 `/instant-chat` 已返回 202，随后日志出现 LLM/工具超时或 retry：判为 Worker 到模型供应商/工具链问题。
   - 若只有 `emotion-eval` warning 而主任务随后成功：只记录副评估失败，不归因为主生成故障。

下次用户说“云端又卡住了”并提供日志时，应先按本节把同一任务 UUID 的前端请求、Worker 起跳、模型调用、
重试和最终送达串成一条时间线，再决定是否需要修改超时、重试或入口域名；不要在没有对应日志时猜测或改代码。


二十一、角色睡眠期间暂停思念值增长（2026-09-02）
------------------------------------------------

1. 思念值不再按整段墙上时间无条件增长。前端同步关系状态时，会读取角色当天日程，把明确写为睡觉、
   睡眠、午睡、补觉等的槽位延伸到下一条日程开始，作为角色当地时区的睡眠窗口传给 Worker。
2. Worker/D1 把最近一次睡眠窗口保存在关系加密账本内。即使用户关闭小手机，Cron 推进思念值时也只累计
   清醒时间；睡眠期间增长为 0。日程暂时不可用时，才用该角色关系设置里的免打扰起止时间作睡眠兜底。
3. 每次计算后 `lastCalculatedAt` 都推进到当前时间，包括整段都在睡眠的情况。因此角色醒来后不会把昨夜
   被跳过的时长一次性补涨回来；手动校正后的数值仍作为新的基线继续按清醒时间自动计算。
4. 前端关系卡的本地即时估值也扣除免打扰睡眠时段，避免 Worker 回包前先在界面上显示一夜暴涨的旧估值。
5. 本规则只暂停思念值的时间增长，不改醋意事件、用户回复回落、发送成功后的 6/8/10 点释放、+30 阈值、
   每日上限、最短间隔或强制联系规则。
6. `worker/amsg/worker.bundle.js` 已随源码重新构建。要让小手机关闭后的离线计算采用本规则，必须用该正式
   AMSG bundle 更新现有 Cloudflare Worker；不能部署仅供预览的 `worker/moments/worker.bundle.js`。
