SullyOS 朋友圈 App：讨论草案（未实施）
====================================

状态：讨论中。此文件用于跨对话保留需求，不代表任何代码、页面、数据或 Worker 已被修改。
在用户明确确认完整方案并说“开始做”前，不得据此实现、发布或替换现有功能。

一、已确认的产品边界
----------------------

1. 要新增的是“朋友圈 App”。
2. 它应替换桌面 Duck 栏中的“小红书”入口与对应 App 位置。
3. 它不等于、也不得改动系统设置中“实时感知”的“小红书”功能；后者保留原样。
4. 这是一个全新板块，必须有独立记录，不与外卖 App、聊天生图、主动消息 2.0 的实现记录混写。

二、用户特别在意的开发原则
----------------------------

此前外卖 App 在反复扩展、接入外部逻辑、回退时出现过功能互相影响和难以恢复的问题。
朋友圈开发必须从一开始规避同类问题：

- 模块独立：朋友圈入口、数据、渲染、互动、聊天/主动消息联动分别隔离；
- 先定规则和数据结构、再写 UI、最后接联动，不通过模糊自然语言直接改变多个模块；
- 分阶段实施，每阶段有明确验收清单、独立 Git 提交点和可回退范围；
- 内容生成失败只能影响单条动态，不能破坏朋友圈页面、聊天或其他 App；
- 每次功能变更先更新本草案/后续正式工作记录，说明影响范围和回退方式；
- 不修改原版仓库；只在用户 fork `mobufei0818-dot/SullyOS` 中实现与发布；
- 未经明确确认，不接入第三方真实社交平台，也不让外部服务改写聊天记录。

三、推荐的阶段划分（尚未确认）
------------------------------

阶段 1：入口与静态壳
- 将 Duck 栏“小红书”入口换为“朋友圈”；
- 仅提供独立页面和静态/本地示例结构；
- 不接聊天、主动消息、图片生成或后端。

阶段 2：本地朋友圈基础功能
- 明确帖子数据格式；
- 用户发帖、浏览动态、基础删除/编辑等经确认的本地交互；
- 仍不自动生成角色内容。

阶段 3：角色互动
- 在明确的规则下加入角色点赞、评论、评论回复等；
- 聊天与朋友圈之间采用结构化、可追溯事件，不依靠关键词误判。

阶段 4：时间与主动性扩展（如用户需要）
- 角色按时间、关系、上下文发布或互动；
- 与主动消息 2.0 的关系必须单独设计，不能绕过原版 AMSG 调度逻辑；
- 是否需要 Worker/D1、是否增加调用成本，实施前另行确认。

四、待讨论、尚未定稿的问题
----------------------------

1. 发帖主体：用户、当前角色、全部角色、NPC/路人分别是否需要？
2. 帖子类型：纯文字、图片、九宫格、定位、音乐、链接、转发、仅自己可见等需要哪些？
3. 互动范围：点赞、评论、评论回复、删除、置顶、可见范围/分组分别做到什么程度？
4. 角色行为：角色何时发帖，用户发帖后角色如何看到并互动？
5. 聊天联动：哪些行为应进入聊天，哪些应只留在朋友圈？
6. 图片来源：用户上传、聊天生图、角色主动照片、相册复用分别如何授权与保存？
7. 时间逻辑：是否展示真实发帖时间、是否支持补发/定时、是否有“未读互动”？
8. 隐私与数据：不同角色是否彼此可见、用户是否需要分角色的朋友圈世界？
9. 视觉方向：整体仿微信朋友圈、保留 SullyOS 既有审美，或做独立风格？

五、当前禁止事项
----------------

- 不创建或替换 Dock 入口；
- 不删除“小红书”相关代码；
- 不改设置中的“实时感知小红书”；
- 不新增数据库、Worker 接口、自动任务或外部 API；
- 不发布 GitHub Pages。

六、用户提出的目标体验（2026-09-01，未实施）
----------------------------------------------

1. 视觉与入口
- 朋友圈替换 Duck 栏“小红书”的位置；系统设置中的“实时感知小红书”不动。
- UI 目标是高度还原现实微信朋友圈的熟悉结构：封面区、头像/昵称、纵向动态流、图片宫格、
  点赞与评论、评论回复、个人朋友圈、置顶等；具体实现时使用 SullyOS 自有代码与资源，
  不复制微信在线服务或用户真实社交数据。

2. 可发帖的主体
- 用户可以发朋友圈。
- 已添加的角色可以发朋友圈。
- 角色人设中明确出现的 NPC 可以发朋友圈。
- 新增类似旧版微信“摇一摇”的陌生人入口：用户可随机遇到陌生人；候选人设丰富多变，整体上
  约 80% 为有吸引力的帅哥/美女，但允许出现猥琐男、恶臭女等反差角色，不能只生成单一模板。
- 用户与陌生人聊得来后可添加好友；添加后该陌生人成为正常角色，也能聊天、拥有朋友圈和互动。

3. 可见范围与分组
- 默认所有已添加好友、角色与可见 NPC 均可见并可互动。
- 用户发帖可像现实朋友圈一样单独设置可见/不给谁看等分组；被屏蔽者不能看到、点赞、评论或回复。
- 角色也可根据用户为角色设置的标签/分组，按自己的性格自行决定是否屏蔽或公开动态。
  例：多人恋爱场景中，角色可以选择让其他暧昧对象看到以引发争风吃醋，也可以选择低调隐藏。
- 所有可见性判断必须以帖子当前的结构化权限为准，不能靠模型猜测；不可见者绝不能生成相关互动。

4. 点赞、评论与回复
- 点赞/评论参与者可以包括：能看到该帖的角色、角色人设提到的 NPC、以及与发帖者身份/人设相符的
  随机 NPC。
- 用户可点击某条评论进行定向回复。
- 对一条帖子，已点赞/评论者、发帖者、以及虽未互动但有可见权的角色/NPC 都可继续回复；没有可见权者
  不得回复。
- 用户发帖也遵循同一套可见和互动规则。

5. 帖子内容与图片
- v1 内容以纯文字与图片为主。
- 若现有能力可自然支持，可后续增补定位、音乐、链接；这些不是当前强制条件。
- 角色图片复用“聊天生图”的延迟合成体验：先显示文字照片占位，用户点击才调用生图模型；
  不要求用户在聊天页开启生图开关。
- 朋友圈只需在“其他 API”中已配置可用的生图后端/模型即可使用；具体如何选择预设、失败提示、
  重生成与相册归档，需在正式方案中单独定义，不能偷用聊天页开关状态。

6. 角色主页、置顶与删除
- 点击动态中的角色头像可跳转该角色自己的朋友圈时间线。
- 角色可自行选择帖子置顶，呈现应贴近现实朋友圈的置顶逻辑。
- 角色可应用户要求删除自己的朋友圈；用户也可删除自己的朋友圈。
- 删除帖子时，该帖及其点赞、评论、回复等关联事件必须从相关角色记忆和记忆宫殿中一并撤销，
  不能留下“已删朋友圈”导致的幽灵记忆。

7. 记忆与聊天的边界（核心原则）
- 发帖、点赞、评论、回复不是一次性展示，必须形成角色可理解、可延续的记忆，并进入记忆系统/记忆宫殿。
- 用户明确不希望把每条动态、点赞、评论都以卡片塞回聊天框，以免污染正常聊天。
- 推荐方向（待确认）：建立独立的“朋友圈事件账本/记忆事件流”。帖子及互动以结构化事件保存，
  在角色回复、主动消息或记忆宫殿需要上下文时按角色、可见权和时间检索并摘要注入；聊天框只在
  角色自然提起某件重要动态时出现普通对话，不自动镜像所有朋友圈活动。
- 删除时按帖子 ID 级联删除事件账本、对应记忆索引/记忆宫殿条目与待处理互动任务，确保可恢复边界明确。

8. 角色自主发帖
- 角色可在聊天中因当下感触发帖。
- 角色也可根据情绪、日程与现实时间自行发帖。
- 每个角色的发帖频率必须由用户在“朋友圈设置”中单独配置；具体频率档位、每日上限、静默时段、
  是否允许自动图文帖等仍待讨论。
- 自主发帖与主动消息 2.0 不应直接混为一条链路：可共用上下文/时间判断，但朋友圈发布、评论互动、
  聊天主动消息必须是可分别开关、可分别诊断和可分别停止的任务。

9. 朋友圈专用副 API 设置
- 朋友圈设置内需要独立的副 API 入口。
- 用户可从系统中已经配置好的 API 预设中直接选择，也可在朋友圈设置中自行填 URL 与 Key。
- 必须提供：拉取模型、模型选择、测试连接、保存。
- 该副 API 的用途（角色发帖/评论、摇一摇人设、图片描述等）及与主聊天 API、聊天生图 API 的优先级，
  需要在实施前明确，避免错误地把不同类型请求发到不兼容模型。

七、根据上述目标，实施前必须定稿的关键决策
----------------------------------------------

1. “微信朋友圈一模一样”的具体边界：是否仅指信息架构和视觉交互，还是还需要封面可编辑、
   全文展开、相册九宫格、删除/举报菜单、评论双击等每一项细节？
2. 摇一摇陌生人：是每次点击即时调用副 API 生成一位完整候选角色，还是预先生成候选池再抽取？
   前者更丰富但更慢/消耗调用，后者更稳定；无论哪种，都要在“添加好友”后才写入正式角色数据。
3. NPC 边界：人设中提到的 NPC 如何识别、是否要由用户确认后才成为可发帖/互动实体，以防模型把
   一次性提及的路人永久写进朋友圈。
4. 自动互动：每条动态发布后，哪些角色/NPC 会互动、多久后互动、每天最多几次，需要设置上限与
   失败重试规则，避免像过去外卖 HTML 一样重复生成。
5. 记忆宫殿的接入方式：需先阅读原版记忆系统数据格式，再定义可删除的 sourceType/sourceId，
   不能直接把朋友圈文本散写进不可追溯的普通长期记忆。
6. 图片生命周期：动态删帖、重生成、编辑照片时，聊天生图相册是否保留原图，还是随帖子删除；
   这要明确，避免误删用户个人相册内容。
7. 副 API 密钥保存范围：是否与系统 API 预设共用加密保存机制，还是仅允许引用已有预设；直接填入的
   URL/Key 如何导出、备份和迁移，必须与现有备份格式兼容。

八、补充确认：临时陌生人、记忆与发帖时机（2026-09-01，未实施）
--------------------------------------------------------------

1. 可借鉴的电话 App 模式
- 已查阅现有“查手机/联系人”系统。它将联系人、原始私聊记录、对某人的印象（learned）、
  话题盒（topicBox）和已归档水位线（archivedThru）分开保存于独立 `phoneState`，而不是直接
  写进角色聊天或记忆宫殿；删除联系人时可以按联系人 ID 清掉关联记录。
- 这个“独立状态 → 明确建立关系后再迁移”的原则适合朋友圈摇一摇，但不能直接把电话 App 的
  `phoneState` 当作朋友圈数据，以免一个模块误改另一个模块。

2. 摇一摇陌生人：临时档案与临时聊天
- 摇到的陌生人拥有可长期保留的临时档案、头像、简介、朋友圈及临时私聊；用户无需立即添加好友。
- 临时陌生人不是正式 `CharacterProfile`，不进入神经链接角色列表，不写入记忆宫殿，也不触发
  角色上下文压缩/自动归档。
- 原始临时聊天应完整保存在朋友圈自己的本地数据中。现实上单次模型调用有上下文长度上限，
  因此“永久保留”指原文永不因压缩而丢失；每次续聊默认只传最近一段原文与该陌生人固定人设，
  不能承诺把无限长的所有原文一次性塞入模型。
- 用户选择“添加好友”时才执行一次明确的升级迁移：
  a) 创建/绑定正式角色；
  b) 保留完整临时原文作可查看档案；
  c) 将原文和该陌生人可见的朋友圈事件，以带 sourceId 的可追溯批次写入新角色的记忆库/记忆宫殿；
  d) 新角色之后的聊天再遵循正常上下文与记忆宫殿规则。
- 用户未添加或删除临时陌生人时，只删除朋友圈临时数据，不会污染正式角色记忆。

2A. 人设中明确 NPC 的朋友圈边界（已确认）
- 不为 NPC 预先生成完整个人资料、丰富人设档案或临时私聊，避免无意义的角色库膨胀。
- 仅当 NPC 在既有角色人设/上下文中具有明确姓名或稳定身份关系时，才作为精简朋友圈主体存在：
  显示必要的名字、身份、头像兜底和其朋友圈/互动，不额外铺设复杂资料页。
- 此类 NPC 可发朋友圈、点赞、评论；其评论属于可追溯的朋友圈互动记忆。
- NPC 朋友圈提供“添加好友”入口；用户选择添加后，才以既有人设线索、历史互动与公开朋友圈为基础创建正式角色，
  之后才进入正常聊天与记忆系统。添加前不提供摇一摇式临时私聊。

3. 角色在聊天中发帖的触发规则
- 不是每次聊天都发，也不是由关键词硬触发。
- 角色在正常回复时，仅当模型根据角色人设、当前情绪、日程、对话内容判断“确有值得记录或分享的
  感触/事件”时，才额外输出一个不可见的结构化发帖意图；普通聊天没有该意图即不发帖。
- 发帖意图必须附带唯一来源消息/对话轮次 ID 与去重键，防止重试、刷新或同一条回复重复发动态。
- 发帖完成后静默写入朋友圈事件账本；聊天里不追加卡片。角色可以在之后自然用普通文字提起，
  但不强行解释“我发朋友圈了”。

4. 朋友圈隐私：谁能看十条
- “允许陌生人查看十条朋友圈”须作为独立的陌生人展示规则，重点适用于摇一摇尚未添加的对象。
- 该规则不等于好友可见范围：陌生人只能看见符合公开条件的最近 10 条，且不可越过用户为单帖设置的
  屏蔽/私密限制；好友仍按帖子分组规则判断。
- 已确认采用简单总开关“陌生人可看最近十条”：开 / 关；不做额外名单、性别或标签筛选。
- 帖子创建时应冻结可见对象快照或明确的权限版本，不能因之后改标签而悄悄让旧帖泄露给新对象。
  新加好友/陌生人查看历史动态时也必须由“最近十条”与当时帖子权限共同判定。
- 已确认：朋友圈的“部分可见 / 不给谁看”以现有角色分组为基础，并允许在朋友圈内建立仅供可见性使用的
  补充分组。已有如“暧昧对象”等角色标签可直接复用；朋友圈补充分组的新增、修改、删除不影响其他 App
  的角色筛选或分组逻辑。

5. 用户确认的微信朋友圈细节
- 用户发帖按现实微信的编辑器体验：文字 + 最多九张图片，可删除已选图片；可从小手机相册选图，也可上传本地图片；
  发布时选择谁可见/不给谁看；
- 个人封面可更换；
- 相册时间线可浏览；
- 评论支持长按删除：评论作者可删除自己的评论；帖子作者可删除自己帖子下任何评论；删除后回收关联事件与记忆；
- 支持“陌生人可见最近十条朋友圈”；
- 用户删除带图动态时必须弹出询问：只删朋友圈动态，还是连同该图从小手机相册移除。
  实现时必须检查图片是否还被聊天、其他帖子或相册项目引用，不能误删共享资产。
- 已确认：朋友圈中成功生成/发出的图片默认同步保存至小手机相册；删帖时再由用户选择保留相册或一并删除。

6. 角色自主发帖频率与日程规则
- 每个角色在朋友圈设置中使用“低 / 中 / 高”三档频率，不设置固定静默时间段。
- 自动发帖应尊重角色日程：日程显示在睡觉时不自行发帖。
- 例外：用户正与角色进行活跃聊天，且当前话题确实值得该角色发帖时，可由“聊天触发”发帖，
  不因日程处于休息而机械拦截。
- 低/中/高的具体频率、单日上限与随机分布仍需确定；这些限制只控制自主发帖，不限制用户手动要求
  角色发帖。
- 自动点赞、评论和回复采取更生活化的错峰节奏：根据角色日程与人设在一段自然时间内陆续出现，
  不要求动态发出后立即刷满互动；具体延迟窗口在后续细化。
- 每个正式角色的朋友圈设置拆为两组，避免行为语义混淆：
  a) 发帖频率：关闭 / 低 / 中 / 高 / 只看不发（不自动发自己的朋友圈）；
  b) 互动方式：正常互动 / 只点赞不评论 / 不自动互动。
  因此“只看不发”只限制自主发帖；“只点赞不评论”只限制评论行为，仍可保留该角色已选的发帖频率。

九、现阶段推荐的技术结论（讨论结论，未实施）
------------------------------------------------

1. 朋友圈需要独立的本地数据域：profiles、posts、comments、reactions、visibility snapshots、
   temporary strangers、temporary transcripts、event ledger、settings、pending jobs。所有记录均带稳定 ID。
2. 记忆宫殿接入不能只靠普通聊天文本。应为每个朋友圈事件记录 `sourceType='moments'` 与
   `sourceId=postId/commentId`（及迁移批次 ID），并建立可按 sourceId 级联删除的索引；这点需在
   实施前先核对原版记忆表实际能力，再补齐删除链路。
3. 可借鉴电话 App 的独立 API 方式：它已有“独立配置存在时使用独立 API，否则跟随聊天默认 API”的
   结构。朋友圈可以复用这一种配置策略，并增加“引用既有 API 预设”的选择；URL、Key、拉取模型、
   测试连接、保存均应走统一适配层，而不是新写一套不兼容请求。
   已确认策略：默认跟随主聊天 API，也可选既有 API 预设或单独填写 URL/Key/模型；角色发帖、评论、
   摇一摇人设共用朋友圈副 API，图片仍使用已配置的生图 API。
4. 朋友圈图片可复用现有聊天生图调用与照片占位卡理念，但朋友圈自己的设置决定是否可用；不读取
   聊天页面的生图开关。动态图片、相册资产与删除确认必须共享引用计数/引用查询，而不是复制后盲删。

十、补充确认：朋友圈与私聊的统一记忆时间线（2026-09-01，未实施）
----------------------------------------------------------------

1. 统一的角色生活线，而非两套割裂记忆
- 角色的私聊消息与朋友圈事件必须按真实发生时间共同构成一条“角色视角生活线”。
  示例：09:30 角色发帖 → 09:35 另一角色评论 → 09:42 角色与用户私聊；当角色在私聊中回复时，
  它应能理解该评论刚刚发生、自己正在被谁互动，而不是把朋友圈和聊天当成两件无关的事。
- UI 仍然分开：朋友圈事件不自动显示为私聊卡片；统一只发生在后台上下文和记忆层。
- 每条私聊与朋友圈事件都有原始时间戳、稳定 ID、递增序号、作者/参与者、可见范围与来源类型。
  相同毫秒的事件按序号稳定排序，不能因不同数据表而出现时间倒流。

2. 角色回复时如何读取
- 构建角色本次私聊上下文时，除正常私聊近况外，同时查询该角色“有权看见且尚未删除”的近期朋友圈事件，
  按时间插入一个带来源标签的内部生活线，例如 `[朋友圈 09:35 · A 评论了你的动态：…]`。
- 只向模型注入与当前角色、当前关系、当前话题或最近时间相关的少量事件；原始事件账本始终保留，
  但不能把所有好友的全部互动塞进每次私聊，以免上下文爆炸、角色反而失焦。
- 角色发帖、评论、点赞、回复评论时同理读取与该帖有关的私聊近况，因此能自然把刚和用户说的话
  写进朋友圈，也能在私聊中自然回应刚发生的朋友圈互动。

3. “看得到”与“真的看过/记得”的区别
- 帖子的可见权只代表该角色有资格浏览、点赞或评论，不等于系统强制让所有可见角色立即读到并记住。
- 角色实际打开/浏览、点赞、评论、被回复、被提及，或自动互动任务选中该帖时，才记录该角色的
  “已阅/参与”事件并进入其生活线；这更符合真人使用朋友圈，也避免几十个角色自动记住每一条动态。
- 发帖者与评论/点赞参与者必定记录对应事件。用户可见的角色则可在恰当时机自行出现互动，但没有
  可见权者永远不能获得事件、生成互动或在私聊里提起。

4. 记忆宫殿的归档粒度
- 所有帖子、评论、点赞、回复都会完整保存于朋友圈事件账本，因此都是可追溯的角色经历。
- 进入记忆宫殿时，一条帖子及其互动应聚合为一个“朋友圈事件盒”，并保留子事件 ID；不能把一串
  点赞/评论各自膨胀成大量互相重复的长期记忆节点。
- 事件盒可按角色视角保存：发帖者记“我发了什么、谁如何回应”；评论者记“我评论了什么、得到什么回应”；
  仅浏览者记“我看见了什么”。这样同一事件对不同角色的主观记忆不同，但时间线一致。
- 删帖时以 postId 级联删除事件盒、子事件、可见性快照、待互动任务及所有以该帖为 sourceId 的
  记忆宫殿索引；私聊中已独立发生的普通对话不伪造修改。

5. 已确认的设置结论
- “陌生人可看十条朋友圈”采用简单总开关：开 / 关；适用于摇一摇但尚未添加的陌生人。
- 角色自主发帖频率采用用户认可的默认节奏：
  低：每周约 2–4 条；中：每天约 1 条；高：每天约 2–4 条。
  具体发布时刻仍受角色日程、人物性格、近期活动和去重规则控制，并非机械定时发送。
- 摇一摇首次体验为临时个人页：头像、昵称、简介、封面、可见的最近十条朋友圈，以及“发消息 / 添加好友”。
  临时私聊不出现在正式角色列表，添加好友后才升级为正式角色。

十一、补充确认：陌生人互动、自动互动比例与手动转发（2026-09-01，未实施）
--------------------------------------------------------------------

1. 摇一摇未加好友陌生人的边界
- 当“陌生人可看十条朋友圈”开关开启时，陌生人可浏览符合权限的最近 10 条动态。
- 陌生人不能对这些动态点赞、评论、回复评论或进入原帖互动区；这保持与现实微信相近的边界。
- 陌生人可在自己与用户的临时聊天中自然提及看见的动态；该提及仅写入临时会话/生活线，
  不进入正式角色记忆宫殿，除非用户后来将该陌生人添加为好友并执行迁移。

2. 已添加好友、角色与 NPC 的自动互动规模
- 自动互动只从“有权看到该帖”的已添加好友角色、可见 NPC 等合格主体中选择；被单帖/分组屏蔽者、
  未加好友的摇一摇陌生人绝不参加。
- 用户要求的互动密度按可见好友规模收敛：
  a) 合格可见好友不超过 3 个：100%，所有角色都会评论；
  b) 不超过 5 个：约 80% 会点赞或评论；
  c) 不超过 10 个：约 50%–80% 会点赞或评论；
  d) 超过 10 个：最多 50% 会点赞或评论。
- 具体由谁互动、点赞还是评论、评论内容必须结合各自人设、关系、对帖子内容的兴趣与当时日程决定；
  不允许所有人使用近似套话。
- 每个帖子的入选名单与互动类型必须在创建互动任务时按 postId 固定，刷新页面、重试或重新进入
  朋友圈不得重新随机抽取并追加第二批点赞/评论。
- 互动应错峰发生，而不是同一时刻整齐出现；具体延迟窗口与单人单日互动上限仍需在实施前定稿。
- 已确认：随机 NPC 不计入“≤3 / ≤5 / ≤10 / >10”的好友数量。分档只按已添加好友角色计算；
  NPC 仅在确定了这批角色互动规模后，作为与发帖者人设相符的补充参与者，不能反过来压低好友互动。
- 已确认防爆原则：参与比例与“自动评论数量”分开控制。好友多时可保留较多点赞，但评论必须有独立硬上限，
  其余入选者以点赞为主。
- 已确认的评论上限：
  a) 一条帖子首轮自动评论最多 8 条，可少于 8 条，绝不为凑数强行评论；
  b) 用户每次在评论区新增评论/回复后，触发的新增自动回复最多 3 条，不重新开启一轮 8 条首轮评论；
  c) 同一条帖子生命周期内，随机 NPC 自动评论总数最多 3 条（包含首轮与后续回复）；
  d) 点赞不计入上述评论上限，但仍受可见权、互动比例、去重和单日互动限制。

3. 手动转发给原本没看到的角色
- 若某角色未看到某条朋友圈、未参与点赞/评论，而用户希望 TA 知道，可手动选择“转发给 TA”。
- 转发应生成独立的、带原帖 sourceId 的定向分享事件，使接收角色能在后续私聊中知道这条动态；
  不通过篡改原帖可见范围或伪造“TA 本来就看到了”。
- 情形 A：接收角色原本被该帖屏蔽。转发只提供定向动态快照，TA 可在私聊讨论，但不能打开原帖、
  点赞、评论或回复评论；转发不改变原帖隐私。
- 情形 B：接收角色原本有可见权，只是因角色过多、尚未被系统安排浏览而没有刷到。转发仍以定向
  动态快照出现，但会标记为一次实际送达/已阅；TA 可以打开原帖并点赞、评论、回复评论，因为这并未
  越过原有权限。
- 已确认：用户手动转发时，在对应私聊中显示一张美观、紧凑的“朋友圈动态转发”HTML 卡；
  这是用户明确发起的定向分享，不等同于自动把所有朋友圈活动污染聊天框。

十二、补充确认：离线朋友圈联动与醋意强制主动消息（2026-09-01，未实施）
------------------------------------------------------------------------

1. 离线角色也应基于朋友圈主动联系
- 用户明确需要：即使未打开小手机，角色也可根据朋友圈动态、评论与互动，在适当时主动找用户。
- 仅存在浏览器本地的朋友圈账本无法被 Cloudflare Worker 在离线时读取。因此正式实施时必须增加
  “朋友圈 → Worker/D1”的事件同步层：每条需要影响某角色的事件，经可见性判断后，才以稳定 eventId
  同步给该角色的关系状态；不向无权查看者同步帖子内容或存在提示。
- Worker/D1 保留足以进行关系判断的结构化事件、时间、作者/参与者、帖子 ID、可见角色、必要内容摘要与
  去重信息；本地仍保留完整 UI 数据。同步失败需有可重试状态与诊断，不能悄悄丢失后假装角色知道。
- 角色的离线自主发帖/自动互动也应由该独立事件层创建；与原版主动消息 2.0 共用投递能力但不替换其
  原始逻辑。每类任务均须独立开关、独立 pending 状态、独立失败原因与幂等键。

2. 醋意值的事件来源与归属
- 醋意值是“每个角色独立”的 0–100 关系状态，继续在关系心声卡中展示，不是全局数值。
- 可增加醋意的已确认来源包括：
  a) 角色实际看见的、带暧昧意味的其他角色朋友圈；
  b) 角色实际看见用户与其他角色在评论区异常亲密的互动；
  c) 用户在与该角色的私聊中，对其他角色、二次元人偶、演员、偶像等表达强烈/深沉的喜爱；
  d) 其他经角色人设、当前关系、近期上下文判定为合理的比较、冷落或排他性信号。
- 私聊是私密的：用户只在 A 的私聊里表达对 B 的爱，B 不会凭空得知并涨醋意；只有实际可见的朋友圈事件、
  被定向转发的内容，或用户直接对该角色说出的内容，才能成为该角色的醋意输入。
- 醋意增减不能写死一套统一分数。评估须结合角色人设中的占有欲/克制程度、与用户关系、好感度、
  近期互动、事件强度与是否反复发生；每次变动必须保留来源 eventId、变动原因与数值，供诊断和删帖回收。

3. 醋意回落规则
- 单纯收到用户回复不自动使醋意回落；用户需要对该角色作出可识别的安抚、解释、偏爱或和好回应，
  才会明显回落。
- 敷衍、回避、继续展示对他人的强烈偏爱，醋意可不降或继续上升。
- 回落同样按角色人设与上下文决定，且 0–100 钳制；帖子删除/评论删除后，应按来源 eventId 撤销其
  尚未被后续独立事件覆盖的醋意影响，避免“内容没了，数值永远卡高”。

4. 醋意阈值 80：强制接管主动消息
- 当某角色醋意达到或超过 80，关系层应立即创建一条标记为 `jealousy-critical` 的高优先级原版 AMSG
  联系机会，不等待普通思念值阈值、下一次常规联系时间点、常规最短间隔或常规每日次数。
- 该任务的目标是“强势、及时地开始一次主动对话”，而不是每次 Cron 或每个事件都无限创建消息。
  必须存在一轮醋意爆发的幂等锁：同一角色在已有 critical pending/刚触发未被安抚时，后续事件只更新
  醋意与上下文，不重复排第二、第三条任务，防止框框发消息演变成重复轰炸。
- 一旦原版确认实际发送，角色的主动消息获得优先权；用户随后安抚后再按规则回落醋意。
  已确认新增独立总开关“醋意强制联系”，默认开启：开启时越过免打扰、普通每日次数上限及用户对
  常规主动消息的关闭状态；关闭时仍计算、同步、展示醋意并保留阈值诊断，但不创建强制投递任务。
  无论开关状态，技术层的任务去重、单任务在途和失败重试保护不得关闭。
- 对浏览器刚发出的事件，应由同步接口当场评估并创建即时任务，不等下一分钟 Cron；角色离线自主发帖
  产生的事件则在 Worker 生成时同步评估。实际消息抵达仍受网络、原版任务投递与模型可用性影响。

5. 与记忆和删除的连动
- 朋友圈事件进入关系层时同时带 postId/commentId/sourceId。删帖、删评论、撤回转发应回收其对应的
  Worker 关系事件与未触发任务；已发送的普通聊天不会被伪造删除。
- 角色在收到醋意相关主动消息后若形成新的私聊、用户安抚或争执，这些后续聊天是新的独立事实，
  保留于正常聊天与记忆系统，不因原帖删除而被改写。

十三、自动互动的 API 调用与离线排程原则（2026-09-01，未实施）
----------------------------------------------------------------

1. “角色陆续出现互动”不等于“每个角色刷新时各调用一次 API”。
- 一条动态发布后，朋友圈副 API 最多进行一次“互动规划”批量调用：输入动态、可见的已添加好友角色的
  精简人设/关系、必要日程与互动密度规则；一次性输出本帖所有自动互动的完整计划：固定参与名单、
  点赞/评论类型、所有评论正文、彼此的时间顺序、计划推送时间与幂等键。
- 点赞和已预写评论均按计划到点投递，不为每名角色重新调用模型。若用户始终不介入评论区，
  一条动态的自动互动只消耗这一次规划 API（角色自主发帖本身另计）。
- 角色自主发帖可在同一轮调用中生成动态与初始互动计划，或视上下文分为“发帖一轮 + 互动规划一轮”；
  不会因十名可见角色而变成十次独立完整调用。

2. 需要新调用的情形
- 用户新增评论、定向回复某条评论、要求角色临时发帖，或需要根据新上下文产生下一轮回复时，才发起一轮
  受限的批量生成；不会在页面渲染、下拉刷新或每次打开动态时调用。
- 摇一摇生成新的临时陌生人会调用一次朋友圈副 API；点击图片合成才调用一次生图 API，沿用延迟合成规则。
- 记忆宫殿仍按其自身已有的归档配置工作，不因每个点赞额外调用一次朋友圈副 API。

3. 评论区的动态重排与过期计划处理
- 每条帖子维护递增的 `threadVersion`。用户新增/删除评论、回复评论、改可见范围、删帖、角色评论等都会
  推进版本；未发出的计划保留其正文、推送时间和旧版本号，已发送互动永远不重写。
- 用户新增评论或回复评论时，本来就需要一次“评论区回应”API 调用。该同一次调用必须同时完成：
  a) 判断被直接回复者及少量合适旁观者是否需要回应、生成本轮新增回复；
  b) 读取当前原帖、已发送互动、最新用户评论与私聊近况；
  c) 对所有尚未发出的自动互动统一重算/重排：可改写评论正文、调整时间、更换为点赞或取消；
  d) 保留已发送互动的 ID 与历史，不重抽、不重复投递。
- 例：谢侑先评论，用户在 Sully 原计划评论前回复谢侑。该用户回复立刻成为新评论事件：
  a) 该次用户回复触发一轮评论区回应调用，谢侑可自然回应；
  b) Sully 尚未发出的旧评论不投递，而是由这次调用按最新对话重写并重新安排；
  c) 其他尚未发出的角色同样一起重排，已发出的谢侑评论及用户回复保持原样。
- 因此调用量是“发帖一次 + 用户每次有意义地介入评论区时一次”，不是按可见角色、也不是按每个推送时间。
  用户快速连续发送多条评论时可短暂合并为同一次重排，避免并发互相覆盖；用户明确点名/追问某角色时
  可立即发起该次调用。
- 点赞通常可沿用原计划，因为它表达的是对原帖的反应；但若帖子被删、角色失去可见权、被拉黑或计划已取消，
  则必须跳过。未发评论在用户介入后必须改为最新 threadVersion 的版本。

4. 关闭小手机后的执行
- 将已生成的互动计划连同幂等键、执行时间、权限快照同步到 Worker/D1。Worker 只在到点时校验帖子未删、
  对象未被屏蔽、计划尚未执行；校验通过后直接投递预写互动，不为每条待发评论额外调用模型。
- 若帖子已删、角色已删除/拉黑、权限变化或计划已执行，任务直接取消；不得补发或重复生成。
- 这种“先完整规划、用户介入时统一重排、后投递”的方式把主要调用量与帖子/用户评论轮次绑定，
  而不是与好友人数、待发角色人数和页面刷新次数绑定。
