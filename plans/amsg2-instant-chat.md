# 主动消息 2.0「即时对话」方案（instant chat）

> 讨论稿。定位：把聊天主路径从「浏览器本地跑生成」换成「云端跑生成」，
> 复用主动消息 2.0 已有的整条管线。少写实现，多写取舍——先把方向钉死再动手。

## 一句话

把每条聊天消息当成一条「立刻触发」的主动消息任务：按下发送 = 一次很小的
POST 上云，生成在用户自己的 CF Worker 里跑完，结果走 Web Push 下发。
客户端发完那一刻就自由了——切后台、杀进程都行，回复到了推送会叫它。

## 为什么要做

现状的聊天路径要求**客户端从发送活到生成结束**，由此背上三个包袱：

| 包袱 | 现状 | 改完 |
|------|------|------|
| fire_pack 补传 | 打脏后微任务内立即上传，同一轮的连环打脏合并成一次 | 机制整个退役——上传发生在按发送那一刻，前台必然可见 |
| presence 心跳 | 生成期间每 15s 两个请求，请求数正比生成时长（等 2 分钟 ≈ 20 个请求） | 归零——worker 自己知道这轮在跑，不需要客户端举手 |
| 生成期间被杀 | 切后台几秒就可能被杀，这轮白等 | 无所谓，云上照跑，回来收推送 / 拉收件箱 |
| 走 Deno 门面的额度 | 未验证组织 1 万请求/月 ≈ 每天 17 轮（按 2 分钟生成算） | 每轮 1 个请求 ≈ 每天 330 轮 |

这个方案是把包袱直接卸掉。

## 设计要点（高层）

1. **触发**：新端点，POST 带上增量消息 + 本地游标（最后一条消息 id + 条数），
   worker 回 200 = 已受理，几十毫秒的事。门面的 105s 首字节、SSE 送达判定
   那些约束全都不再适用——没有任何一条长连接。
2. **生成**：先落盘再开跑，双保险。POST 把一条「立即执行」任务写进 D1
   （落盘即受理），同一个请求里 `ctx.waitUntil` 马上跑生成；isolate 被
   回收的话，cron 下一分钟捡起仍 pending 的行接着跑。任务行带认领标记
   （认领时刻超时才允许 cron 接手）防双跑。体感：waitUntil 活着 = 秒开跑，
   死了 = 最坏 +60s，正确性两头都兜住，不依赖对平台行为的预判。
3. **生成管线**：复用主动消息 2.0 fire 现有那套——工具循环、表情包、
   实时世界、后台 MCP 都是现成的。**这次 POST 顺手把 fire_pack 也更新掉**，
   到点的定时任务和即时对话共用同一份上下文，补传机制才真正退得掉。
4. **送达**：Web Push（CF 直发手机，不过门面）。通知一定弹，但同一个角色折叠成
   一条，用户看着页面时不响、切后台照常响铃；消息本身照旧由 SW 转给页面上屏；
   推送丢了靠上线拉收件箱兜底
   ——收件箱进来后那条 13 步后处理管线是现成的，记忆宫殿等本地后处理照跑。
   上屏体感不变：管线对「刚送达」的消息保留拟人打字节奏（每条气泡之间
   0.5~2s），只有补收（躺超过 2 分钟）才一次性回填，和现在的前端一致。
5. **状态**：D1 存对话历史，但**本地仍是唯一真相**。每次 POST 只传增量，
   worker 用游标对账，对不上（回滚备份、删改消息）就要求整包重传，
   重传走 gzip 上行（大 body 42s 超时的教训已有现成修法）。
6. **失败**：云端生成失败推一条 `messageKind: 'error'`（SW 已有这条分轨）；
   客户端「正在输入」有超时兜底，到点提示失败、可手动重发。

## 已经定下的取舍

- **无流式**。生成期间没有逐字吐出，配「正在输入…」指示：POST 200 亮起，
  push 到达熄灭。等不到就每 60s 去云端点名问一次那条任务的状态，只有云端明确
  说它已失败（或那行没了而回复也取不回）才熄灯、提示可重发；云端还在跑或在
  重试就一直等。回复到端后按打字节奏逐条上屏（见上），体感更像真人回消息。
- **通知一定弹，打扰靠折叠 + 按可见性静音压**：同一个角色在通知栏里只留最新
  一条（同 tag 互相覆盖）。响不响由 SW 收到推送那一刻的窗口可见性定
  （`silent: 'when-visible'`）：用户正看着页面就安静躺着，切后台、锁屏则照常
  响铃震动。同 tag 默认是静默替换，所以每一轮的第一段带 `renotify`，一轮响一
  声、后面几段安静更新内容。订阅是按 `userVisibleOnly` 建的，收到 push 却不弹
  等于跟浏览器违约——Firefox 按配额把订阅退掉、iOS 过了新订阅的几天宽限期一条
  就吊销，两边都静默发生。所以口径是：要推就一定弹，不想弹的内容压根不发推送、
  留在服务端收件箱等客户端上线补拉。
- **不做静默兜底**。显式开关，关掉回本地生成。POST 失败 = 这条没发出去，
  明确报错、可手动重试，绝不悄悄转回本地跑——静默分流那种查无可查的坑
  踩过一次就够了。
- **聊天 API 凭据常驻云端**。AI 模式定时任务本来就这样，即时对话只是让
  每一轮都用它，不是新增暴露面。
- **单用户、单设备假设不变**。
- **开关前置条件**：推送权限已授予才允许打开（不然发得出、收不到），
  没给权限时开关置灰并说明。
- **一次做完整替换，不分阶段发**。amsg2 整条链路已经端到端验证过，
  没有需要分批探路的未知数；下面的施工顺序只是干活的先后，不是一个个
  可发布的里程碑。

## 施工顺序

1. worker 侧通道：新端点 + 立即任务行 + `waitUntil` / cron 双保险 + 认领防双跑
2. 对账与并轨：游标 / 全量重传（gzip）/ fire_pack 由这次 POST 顺手更新；
   退役 presence 心跳和 fire_pack 补传
3. 前端切换：发送路径改走 POST、「正在输入」指示、通知折叠与静音策略
4. 收尾：设置页开关（含置灰）、文档、埋点

## 待查小项（不挡工）

- 已定：群聊不切（收件箱按 charId 路由，群聊没有 charId，见契约「群聊不动」条），继续走本地生成
- 已定：即时对话取代 Instant Push，设置页双向互斥；IP 面板与链路为存量用户保留。
- 那条折叠通知在 iOS 真机上的观感：前台聊天时（该安静躺着）和切后台时（该响铃叫人）
  两种情况都要看，另外确认 iOS 认不认 `renotify`——不认的话新一轮的第一段还是会被
  当成静默替换

## 明确不做

- 流式吐字（沉默期由「正在输入」承担）
- 任何静默回退本地的逻辑
- 多设备同步
