二、用户的总目标
----------------

在保留原版 SullyOS 聊天与备份恢复能力的基础上，制作一个类似美团外卖的“外卖 App”，
它不是孤立页面，而是要和角色聊天、HTML 卡片、角色上下文、主动消息 2.0 互通。

用户强调：
- 每次真实修改后都要更新 GitHub Pages，不能只改本地。
- 刷新与搜索必须调用用户配置的 OpenAI 兼容 API；没有配置应明确提示失败，不能假装刷新。
- 数据要能保留，退出外卖 App 后不应丢失搜索/推荐结果。
- 所有互动要自然地融入聊天，不能只做摆设 UI。

四、已完成的外卖功能
--------------------

A. 首页、分类与分页
- 首页“今日为你推荐”固定 10 个坑位。
- 首页刷新通过 API 获取一整轮 10 个不同商品，替换旧首页推荐。
- 八个分类：美食、甜点饮品、超市便利、蔬菜水果、看病买药、早餐、拼好饭、跑腿。
- 分类初始至少 10 个项目，按每页 5 个展示。
- 分类刷新通过 API 追加 10 个项目，最多保留 30 个；超出时挤掉最早项目。
- 搜索按关键词真实请求 API，返回至少 10 个相关商品，5 个一页。
- 搜索词和搜索结果会本机持久保存，退出 App 后再次进入仍能看到。

B. API 与报错
- “主 API”：沿用 SullyOS 系统 API 配置（URL、Key、模型）。
- “副 API”：外卖 App 内可填写 URL、Key、模型，并可请求 /models 拉取模型列表。
- 只支持 OpenAI 兼容 API。
- API 未配置、网络失败或模型返回格式错误时，调用原版 showError 明确提示。
- 刷新、搜索等请求通过 safeFetchJson，进入原版 API 调用记录。

C. 地址与 POI
- 地址已升级为“地址簿 + 收货对象绑定”：用户和每个角色各自保存默认收货地址，不能再互相覆盖。
- 顶部显示“收货对象 · 地址”，例如“角色名 · 某地”；用户则显示用户昵称（无昵称显示“用户”）。
- 地址设置页可切换“用户地址 / 各角色地址”。切换后，已保存地址下拉框以及下方地址名称、显示收货地址必须立即载入该对象已绑定地址，方便直接修改。
- 地址可保存一次后反复选择；可新增地址。每个地址含名称、显示地址、真实/虚拟模式、虚拟地址映射真实地点。
- 用户从 App 给角色点单：送给角色时用该角色地址；给自己买或让角色代付时用用户地址。
- 角色从聊天给用户点单：始终用用户当前默认地址。
- 真实模式：使用显示收货地址作为 POI 区域上下文；虚拟模式：用映射真实地点作为 POI 区域上下文。
- 高德 Key 是全局设置，但与地址数据分离。地址设置页应提供“测试 POI 连接”，明确显示成功/失败、高德错误码与部分 POI 示例；刷新/搜索最多各请求一次 POI，再把结果作为外卖推荐 API 上下文，不是直接替代模型生成商品。
- 手机端地址设置弹层必须内部滚动、留出安全区；输入框聚焦时应自动滚入可视区，不能被键盘遮挡。
- Key 只保存到当前浏览器 localStorage。GitHub Pages 是纯前端，无法真正隐藏 Key；高德后台应设置域名白名单、配额和限制。若日后需要真正保密，应改为 Cloudflare Worker 代理。

D. 商品详情、口味、规格、价格
- 口味和规格必须分开显示。
- 口味：糖度/冰量/辣度/加不加配料等；按商品类别给出合理项。
- 规格：如中杯/大杯、标准份/加量/双拼、500g/1kg/家庭装等。
- 不同规格可有不同加价；详情页显示“+¥N”。
- 加入购物车后，商品描述会写入口味和规格，商品价格使用规格加价后的实际价格。
- 购物车、结算和 HTML 订单卡都应使用加价后的价格。

E. 购物车与结算
- 可将多个商品加入购物车。
- 底部购物车可点击打开清单。
- 清单支持：逐件勾选、全选/取消全选、删除商品。
- 只有被勾选的商品进入结算。
- 结算页选择“给自己买”、“给某角色买”、“让某角色代付”。
- 点击对象后必须二次确认：显示全部勾选商品、商品小计、取消和确认下单。
- 提交期间按钮锁定，避免重复下单。
- 确认结束后应无论后续提醒创建是否成功都关闭确认层；失败必须明确报错，不能卡住 UI。

F. 用户下单后的聊天与角色认知
- 用户下单后，在对应角色聊天里写入 html_card。
- 卡片包含：商品、价格、配送费、合计、地址、预计送达时间、约需分钟数、支付/送达对象。
- metadata.htmlTextPreview 必须包含纯文本订单事实，供原版聊天上下文读取。
- 订单同时保存到 localStorage：nmj-takeout-orders。
- utils/context.ts 会将最新订单注入角色上下文，特别告知送达前“仍在配送中”。

G. 主动消息 2.0（关键，曾经出错）
- 用户已经部署并启用了主动消息 2.0。
- 早期实现错误地调用 amsg2ToolBridge 的 executeAmsg2Tool('schedule_active_message')。
  这条路径把任务当成“角色自主排程”，会受未回复连发上限限制；被拦截时可能不抛错，
  导致订单已创建但 2.0 面板没有任务，角色也会凭聊天模型猜测而提前说“收到了”。
- 当前正确做法：TakeoutApp 的 scheduleTakeoutArrival 直接调用
  ActiveMsgClient.scheduleCharacterTask，并传 selfScheduled:false。
- 创建出来的任务 source='user'，因此属于用户创建的送达提醒，不受角色自主连发上限影响，
  应显示在主动消息 2.0 任务清单中。
- 创建成功后，用 applyScheduledTask 写回 character.activeMsg2Config.tasks。
- send_at 使用 nowInTimeZone(resolveCharTimeZone(char), etaAt) 生成角色本地墙钟，
  不能直接按设备本地 Date 拼接，否则异国角色会出现时差错误。
- 如果对应角色没有 activeMsg2Config.enabled，应抛出明确错误，不应假装排程成功。
- prompt_hint 要明确：此刻才是预计送达时刻；列出商品；此前不得声称已收到/送达/吃完。

H. 角色主动给用户点外卖（聊天过场）
- 用户澄清：不需要额外的角色下单 API；角色点单是自然聊天过场，但订单数据、小票和提醒必须走外卖 App 的统一后处理。
- 用户明确同意后，角色先自然说一句，再单独输出 `[[TAKEOUT_ORDER: 商品名|价格|规格; 商品名|价格|规格]]`。
- 地址未变化时沿用用户默认地址，不反复确认；支付方式无需确认。
- 仅当用户明确提到旅行、出差、酒店、外地、搬家或当前不在默认地址时，角色才在准备下单前自然确认一次送达地址。
- 用户可在聊天中选择已保存地址，或输入新地址。角色确认后输出隐藏标记：
  `[[TAKEOUT_ADDRESS: 地址名称|显示地址|real或virtual|虚拟地址映射]]`；选择已保存地址可只输出：
  `[[TAKEOUT_ADDRESS: 已保存地址名称]]`。
- `utils/takeoutOrder.ts` 会剥掉地址标记，把新地址保存到地址簿并绑定给用户；当同一轮同时有订单标记时，订单必须使用刚确认的新地址。
- 角色没有得到明确同意时，不能擅自生成订单卡。

I. 移动端体验
- 外卖 App 应处于固定的 PhoneShell 可视区域，不能推动整台手机页面滚动。
- 只有商品内容区可滚动。
- API 设置、定位设置、详情、结算和购物车底部弹层均需内部可滚动。
- 所有固定按钮与弹层都要避开 env(safe-area-inset-bottom)，防止 iPhone Home 指示条遮挡。

nmj-takeout-api

nmj-takeout-orders

六、已知问题与后续修改注意事项

1. TakeoutApp.tsx 当前代码较集中，且有一部分历史兼容逻辑使用 DOM 注入/监听。
   后续如果进行较大 UI 改造，应优先重构为清晰的 React 组件与状态，不要继续增加全局

   25-35 分钟订单，检查任务清单的时间、角色名称、source 和任务状态；不要只看代码。

十一、2026-08-30：地址簿、高德 POI 诊断与旅行地址确认
-------------------------------------------------------

相关代码：
- `utils/takeoutAddressBook.ts`：地址簿存储、旧地址迁移、用户/角色地址解析、高德 POI 测试、聊天确认地址保存。
- `components/takeout/TakeoutAddressSettings.tsx`：移动端地址簿设置页。
- `apps/TakeoutApp.tsx`：顶部对象地址标签、订单按收货对象选址、刷新/搜索 POI 上下文。
- `utils/context.ts`：向角色提供当前用户地址、已保存地址及旅行时确认规则。
- `utils/takeoutOrder.ts`：解析并隐藏 `TAKEOUT_ADDRESS` 标记，先更新用户地址再创建订单。
- `utils/applyAssistantPostProcessing.ts`：即使本轮只确认地址、尚未下单，也必须处理并隐藏地址标记。

关键交互规则：
1. 用户和每位角色各有独立默认地址；地址名称用于帮助用户区分同名城市或多个住处。
2. 外卖 App 顶部地址代表“当前浏览/刷新/搜索所针对的收货对象”；改对象时必须切到该对象绑定地址。
3. 用户给角色买用角色地址；用户给自己买和角色代付用用户地址；角色给用户买用用户地址。
4. 角色不应因为“想点外卖”就机械确认地址。只有用户给出旅行/临时所在地语境时才问；一旦用户确认，新地址保存并成为后续默认用户地址。
5. 角色地址确认和订单可分两轮，也可在同一轮同时输出地址标记和订单标记；程序必须保证订单取最新地址。
6. 高德 POI 连通失败不应阻断外卖 AI 的刷新/搜索，只是本次不提供附近 POI；测试结果必须能让用户看见。

十二、2026-08-30：最终本地角色订单、小票去重与恢复基线（当前有效）
----------------------------------------------------------------

本节优先级最高。若本文件前文的“角色必须先明确同意 / 必须输出隐藏标记”等描述与本节
不一致，以本节为准。它记录的是用户确认可用的最终交互，不要在后续维护时重新加回美团、
待确认单、网页跳转、支付确认或“等待角色说已下单”的门槛。

12.1 最终产品定位

- 外卖 App 是 SullyOS 内的纯本地、剧情互动式外卖系统，不与美团、饿了么或任何第三方
  下单/支付/跳转流程联动。
- 用户在 App 内正常挑选商品、加购物车、结算，订单由本地数据和聊天小票呈现。
- 角色给用户点外卖同样是本地聊天互动：角色并不需要真实付款，也不需要跳转或生成
  “待确认单”。角色、用户和系统都应将其视为已经在 SullyOS 外卖 App 中创建的订单。
- 真实价格、配送费、ETA 是互动展示数据：商品和口味应尽量依据聊天内容；价格、配送费、
  25–35 分钟 ETA 可由程序合理生成，不要求与任何现实平台一致。

12.2 角色给用户点外卖：唯一正确的触发规则

目标：不能因为模型是否遵守一段隐藏格式而时有时无；也不能因同一回复被重复后处理而出现
多张卡。

最终规则：
1. 用户当前这条消息只要明确提出点餐需求，例如“帮我点一杯古茗的超 A 芝士葡萄”、
   “我想吃麻辣小龙虾”、“给我来份早餐”。
2. 角色的下一次回复经过后处理时，程序直接创建一笔本地角色订单并写入一张统一电子小票。
3. 不等待角色说“已经下单”“点好了”“按下去了”；这些话可以自然出现在角色正文里，
   但不是卡片生成的必要条件。
4. 角色仍可输出规范结构标记以提供多商品、价格和规格：
   `[[TAKEOUT_ORDER: 商品名|价格|规格; 商品名|价格|规格]]`。
   标记是增强信息，不是基础功能的唯一入口。
5. 只检查“最新一条用户消息”的点餐意图，绝不从数条前的旧点餐请求再次生成订单；这样用户
   后续说“谢谢”“好呀”或继续普通聊天时，不会反复下单。
6. 用户给角色点餐、角色给用户点餐是两条不同的业务入口；本节只描述“角色给用户点餐”。

12.3 商品名与规格提取规则

- 卡片商品名取用户当前点餐请求中的餐品，不取角色随口编造的店铺/商品组合。
- 已处理常见店名前缀，当前包括：古茗、蜜雪冰城、霸王茶姬、喜茶、奈雪/奈雪的茶、瑞幸、
  星巴克、库迪、茶百道、沪上阿姨、一点点、CoCo、书亦烧仙草、益禾堂、快乐柠檬。
  例如“古茗的超 A 芝士葡萄”在小票中只显示“超 A 芝士葡萄”。
- 角色回复里的少冰、去冰、热饮、全糖/半糖/少糖/无糖/三分糖/五分糖/七分糖、
  大/中/小杯、标准份、加量等会附在商品名后，形成如“超 A 芝士葡萄（少冰、五分糖）”。
- 如果角色使用 `TAKEOUT_ORDER` 标记，标记中填写的多件商品、价格和规格优先，允许一张
  小票展示多行商品。
- 用户没有给出店名时，不要臆造店名；小票只需要商品名。

12.4 统一电子小票与普通 HTML 的边界（关键）

相关代码：
- `utils/takeoutOrder.ts`：订单类型、商品解析、本地去重、保存和唯一的小票模板。
- `utils/applyAssistantPostProcessing.ts`：聊天后处理的“角色外卖订单”步骤，负责落库卡片和
  创建主动消息任务。

唯一小票来源是 `buildTakeoutOrderCard(order)`，写入消息时必须为：
- `type: 'html_card'`
- `metadata.source: 'takeout'`
- `metadata.order: order`
- `metadata.htmlSource: buildTakeoutOrderCard(order).html`
- `metadata.htmlTextPreview: ...`（供角色上下文读取的文本订单事实）

严禁让角色为外卖订单自行输出 `[html]...[/html]` 来代替小票。模型偶尔会同时手写一张
普通 HTML；只要本轮识别到本地外卖订单，`applyAssistantPostProcessing.ts` 必须删除这段
普通 `[html]...[/html]`，只保留统一电子小票。这正是避免“一次出现两张、第一张内容错误”
的修复。普通非外卖 HTML 卡片仍可按原版功能使用，不能一概禁掉。

12.5 同一请求只生成一张卡：去重机制（关键）

数据键：`nmj-takeout-role-order-intents`

- `utils/takeoutOrder.ts` 的 `claimRoleOrderIntent()` 会把已处理的本地订单意图记录在
  浏览器 localStorage 中，最多保留最近 60 个键。
- 对于无隐藏标记的本地订单，键优先使用当前用户消息的数据库 id；没有 id 时使用
  “消息文字 + 时间戳”。
- 对于 `TAKEOUT_ORDER` 标记，键还包含标记正文，以防同一回复被后处理器、流式回填、
  主动消息补收或重试重复执行。
- 同一条用户点餐请求无论处理管线跑几次，只允许：一笔订单记录、一张 html_card、
  一条主动消息 2.0 送达任务。
- 已经显示在历史聊天里的重复旧卡是旧版本产生的历史消息，不应在代码更新时自动删除；
  新订单必须不再重复。

12.6 角色订单的主动消息 2.0 最终规则

- 角色订单落库成功后，若该角色主动消息 2.0 已启用且当前会话配置完整，必须调用
  `ActiveMsgClient.scheduleCharacterTask()`，并使用 `selfScheduled:false`。
- 时间为订单 ETA（创建时随机 25–35 分钟），按角色时区用
  `nowInTimeZone(resolveCharTimeZone(char), new Date(order.etaAt))` 转成墙钟时间。
- 任务记录必须写回 `character.activeMsg2Config.tasks`；这让用户能在主动消息 2.0 面板看见
  已安排任务。
- 送达时的 `promptHint` 必须是：列出本单商品，并自然问用户“外卖到了吗”或“收到了没”。
  绝不能在 ETA 前、ETA 时或之后擅自声称“已收到 / 已送达 / 已吃完”；必须等用户自己确认。
- 角色正文可以自然说“给你点了”，但不得冒出“外卖网关已劫持”等系统化、破坏沉浸感的话。
  后续若再次出现，应修角色上下文提示词，不要改回第三方平台流程。

12.7 当前持久化键总表（外卖相关）

  ETA 和配送状态。

  外卖缓存一起清除，但正常情况下不要删除。

十四、为什么过去会反复出现 HTML 卡片缺失、重复或错位（必须吸取的教训）
-----------------------------------------------------------------------

问题并非“HTML 模板不好看”，而是把同一件事放进了多条互相重叠的链路：

1. 外卖 App 内下单：本应直接创建订单数据和 HTML 卡片。
2. 角色聊天：模型可能输出普通 `[html]`，也可能输出 `TAKEOUT_ORDER` 隐藏标记。
3. 聊天后处理器：会在流式回填、重试、主动消息回放等不同场景被重复调用。
4. 主动消息 2.0：既有角色自己排程的工具链，也有系统替业务排程的链路。
5. 美团半联动尝试：又给“是否真的下单”和“是否该显示小票”加了一层条件。

这些链路曾经同时都能写聊天消息。结果是：
- 有时隐藏标记没被模型输出，卡片缺失；
- 有时普通 HTML 和系统小票都被写入，出现两张或多张；
- 有时聊天重试再次执行后处理，生成五张重复小票；
- 有时为了避免误下单，把触发限制写得过死，用户明确想吃时又不生成；
- 有时主动消息任务写入远端/数据库，但当前 React 状态未同步，面板看似没有排程；
- 有时模型仅从上下文读到旧订单，就在没有新授权的情况下继续说“给你点了”。

核心错误：把“模型理解”“聊天文案”“业务状态”“HTML 渲染”“第三方跳转”和“定时任务”混成
一个隐式流程；其中任何一步不稳定，用户看到的就是随机缺卡、重复卡或错误互动。

未来绝对不要再犯的规则：

A. 一个业务事件只能有一个写入者
- 订单卡只能由一个确定的函数创建；模型不能同时手写同类普通 HTML。
- 不能既让 App 页面写卡，又让聊天后处理器猜测写卡，又让主动消息回放写卡。
- 每笔业务事件必须有稳定 `eventId`，消息写入、订单保存和任务创建都按同一 `eventId` 幂等。

B. 不要让模型隐藏标记成为唯一业务开关
- 模型可以提供商品描述、口味、角色文案等“内容”。
- 是否创建订单必须由明确的 UI 点击或明确的、可审计的用户确认状态决定。
- “想吃”“饿了”不是业务事件；“帮我下单”也应先进入清晰的确认状态，不能靠正则从历史聊天猜。

C. 聊天渲染和业务状态必须解耦
- 聊天卡片是订单状态的展示结果，不是订单本身。
- 先创建/更新结构化订单，再由唯一渲染器把该订单映射为一张卡片。
- 渲染失败要显示明确错误并保留订单，不得静默吞掉；重新渲染只更新同一张卡，不能新增一张。

D. 主动消息 2.0 只能作为订单的后续副作用
- 只有订单已经由唯一写入者成功创建后，才创建 ETA 提醒。
- 任务创建失败不能回滚或重复创建订单卡；要显示失败状态，并允许单独重试任务。
- 任务创建后必须同时写入数据库和当前 UI 状态，用户能在面板立刻核对。

E. 第三方平台一律是可选出口，不得污染本地订单主流程
- 未来若再次考虑美团，只能在已完成的本地订单卡上增加“复制信息/唤起 App”的可选按钮。
- 它不能决定订单是否生成、卡片是否显示、角色是否知情、提醒是否创建。
- 如果第三方 URL scheme 失败，只提示唤起失败；本地聊天与订单绝不能受到影响。


十五、若未来要重新做外卖 App：推荐的唯一安全架构
------------------------------------------------------

恢复不是把已删除文件从历史版本整段复制回来。必须按下面的最小架构重新设计，并先做最小可测版本。

15.1 分层与唯一职责

（1）外卖页面层
- 仅负责商品浏览、搜索、规格选择、购物车和用户点击“确认下单”。
- API 生成商品、POI、地址簿都留在此层；没有 API 时只报错，不伪造刷新。
- 不直接操作聊天消息，不直接调主动消息 2.0。

（2）订单服务层
- 建议新建单一 `takeoutOrderService.ts`，只暴露：
  `createOrder(input)`、`getOrder(eventId)`、`updateOrderStatus(eventId)`。
- `createOrder` 必须生成 UUID `eventId`，并以它做幂等锁：同一次确认无论按钮重复点、网络重试或
  React 重渲染，最多创建一笔订单。
- 订单数据必须先落库，再返回结构化对象；禁止先拼 HTML 再猜订单内容。

（3）聊天展示层
- 建议新建单一 `takeoutReceiptRenderer.ts`，只接收完整 `order`，输出固定电子小票 HTML 和纯文本摘要。
- `writeReceiptMessage(eventId)` 查询现有卡片：不存在才写入；存在就更新同一条，不再新增。
- 普通 `[html]` 与外卖小票使用不同 `metadata.source`，但绝不互相拦截或删除对方。

（4）角色互动层
- 角色想点外卖时，只能先发自然文字提议；用户通过明确、可见的确认动作（如“确认给我点”按钮）
  触发订单服务层。
- 若允许纯文字确认，必须把“待确认意图”单独存为有限时效的状态，绑定“这条角色提议的消息 ID”，
  不能扫描整个历史上下文，也不能仅凭关键词。
- 角色无需知道技术字段或输出隐藏标记；订单创建后给角色注入一条纯文本、明确的订单事实即可。

（5）主动消息 2.0 适配层
- 订单服务成功后异步调用 `scheduleDeliveryReminder(eventId)`。
- 该函数只负责任务：读取订单 ETA、以角色时区创建一次性任务、保存 taskId 回订单。
- 失败时记录失败原因并在订单 UI 显示“提醒未安排”；禁止重跑 `createOrder`。

15.2 必须先完成的测试顺序

第一阶段：只做本地订单（不接模型、不接 POI、不接主动消息）
1. 加三件商品，勾选两件，下单。
2. 连续点击确认五次，只产生一笔订单和一张卡。
3. 刷新页面、退出再进，订单和卡不重复也不丢失。

第二阶段：接聊天展示
1. 用户从 App 下单，目标角色聊天只有一张固定小票。
2. 普通 HTML 卡片仍可正常发送。
3. 角色聊天回复、流式重试、页面刷新均不影响已存在订单卡。

第三阶段：接角色互动
1. 角色先提议，用户明确确认一次，才创建订单。
2. 用户拒绝、换话题、只说想吃时均不创建订单。
3. 同一条确认消息重复处理，仍只有一笔订单。

第四阶段：最后才接主动消息和 POI/API
1. 已创建订单后才创建一条 ETA 提醒，面板即时可见。
2. 任务失败只提示任务失败，订单仍保留。
3. POI/API 失败只影响推荐质量，不影响购物车、下单、聊天卡或提醒。

15.3 恢复前的强制检查清单

- 用户先做“备份与恢复 → 整合导出”，保留可回滚的完整备份。
- 先在新分支实现，不直接覆盖用户正在玩的稳定版本。
- 每完成一个阶段都在手机端实际操作验证；不能仅凭代码阅读或截图判断。
- 每次发布后等待 GitHub Actions 的 `Deploy to GitHub Pages` 成功，再提供
  `?v=<最新短 SHA>` 链接。
- 任何一次出现“缺卡/双卡/多卡”，立即停止添加功能，先用 eventId 和日志定位究竟是哪一个写入者
  写了第 N 张卡；没有查清前不得用更多正则或提示词打补丁。

本节完成后，外卖模块的历史逻辑、删除范围、失败原因和安全重建方案均已记录。未来若用户决定
恢复功能，先读本 TXT 的第十三至十五节，再查看当时的代码与上游更新，不得直接恢复旧实现。
