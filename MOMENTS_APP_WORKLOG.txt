   新朋友圈不能读取、清空、迁移或覆盖旧数据。若要回退，只需将 AppID.Social 映射切回 SocialApp。

二、阶段 0 审计结论（已完成）
----------------------------

1. Dock
   - constants.tsx: DOCK_APPS 已含 AppID.Social；旧标题为 Spark。
   - components/PhoneShell.tsx 与 components/os/appPreload.ts 各自通过 AppID.Social 懒加载旧
     apps/SocialApp.tsx。
   - 因此可以保持 AppID 不变，仅改两处加载映射，旧数据不会被触及。

2. 数据与备份
   - 主 IndexedDB：AetherOS_Data；本次前 schema 为 v71。
   - 历史 Spark 使用 social_posts；新朋友圈独立升至 v72，并拥有 moments_* 自己的表。
   - 完整备份由 DB.exportFullData / importFullData 统一负责。新字段为 momentsData，旧备份没有
     该字段时跳过，不会报格式错误；恢复 momentsData 时只清 朋友圈自己的表。

3. 图片
   - 项目用 blobref 令牌 + blob_assets 保存图片；TokenImg 能正确渲染 blobref/data/http。
   - 聊天照片已与相册共用同一图片引用。朋友圈也只保存 URL/blobref 引用，不复制二进制。
   - 删除朋友圈会明确让用户选择“保留相册副本”或“同时删除关联相册副本”。

4. 生图 / API / 记忆 / Worker
   - 已确认聊天生图共用 utils/imageGeneration.ts；默认不应直接耦合到朋友圈首版。
   - 设置已有 OpenAI 兼容与 NovelAI 生图配置、拉取模型、测试连接；朋友圈专属副 API 留至阶段 4。
   - 记忆宫殿已有 event box、memory source/index 基础；朋友圈需在阶段 3 建立独立 event ledger
     与按角色视角写入，不能把点赞逐条塞进私聊。
   - 主动消息 Worker 已有关系值、诊断和排程；朋友圈的 D1 同步/醋意强制联系留至阶段 4–5，
     禁止在阶段 1 直接改 Worker。

四、阶段 2：权限、角色资料与本地互动（已完成，暂停点）
----------------------------------------------------

本轮已完成的阶段 2 本地层：

1. “谁可以看”不再只是展示文案。发帖可选：公开、部分可见、不给谁看、仅自己。
2. 部分可见/不给谁看会复用既有角色分组，并允许再逐个补充角色；发帖时把分组立即展开为
   最终角色 ID 写进该帖自己的 visibility snapshot。以后改角色分组不会回头改变旧帖的实际受众。
3. 现有正式角色会同步成 moments_profiles 的好友基础档案（名字/头像/角色 ID），只用于
   朋友圈展示；不会创建消息、不会写记忆、不会调用 API，也不会改角色本身。
4. 首页已有“我的朋友”快速查看栏；点击角色头像/名字会进入对应角色的独立时间线。角色/NPC
   自动发帖仍未开放。
5. 点赞、评论与回复已经使用 moments_reactions / moments_comments 本地保存；它们不会自动塞进
   私聊或记忆。自己的评论支持长按删除（桌面端同时支持右键），删除动态会清理关联的本地互动。
6. 朋友圈图片使用应用内大图预览，能正确显示既有 blobref 图片，不再依赖无法识别 blobref 的
   浏览器新窗口。
7. 朋友圈设置已加入逐角色“关闭 / 低 / 中 / 高 / 只看不发”档位并持久化；此刻只是保存用户
   偏好，自动发帖 Worker 还没有接入，避免半成品在后台擅自发内容。
8. 已完成“手动转发给角色”入口：只有用户主动选择角色时，才生成一张简洁的朋友圈转发 HTML
   快照并写入该角色私聊；它会作为用户主动分享的聊天内容参与后续上下文/记忆，而非由朋友圈
   自动污染聊天框。
   - 原本对该角色可见：写 moments_seen_receipts = delivered，后续可视为已送达、可互动。
   - 原本被屏蔽：写 moments_seen_receipts = screened_out，只发送讨论用快照；以后不得反推为
     该角色看过原帖，更不能让他对原帖点赞评论。
   - 每次转发也独立写 moments_shares，保留快照文字、首图引用、实际可见性和时间。
9. “消息”页已经按非用户点赞/评论建立数据驱动的通知列表与红点基础；本阶段还没有自动角色
   互动，因此新安装时保持空状态，绝不会凭空制造角色反应。

五、阶段 3：图片占位、摇一摇与本地记忆事件（已完成，暂停点）
----------------------------------------------------------------

本阶段只接入本地能力，不调用朋友圈副 API、不改主动消息 Worker、不实现自动角色发帖/自动互动。

1. 朋友圈照片占位与点击生图
   - 用户发帖编辑器新增“添加照片占位”；占位卡固定显示照片描述，不会在发表时自动调用模型。
   - 动态中的占位卡只有用户点击后才调用已有 `utils/imageGeneration.ts` 的生图配置；生成中、失败、
     成功均写回 `moments_media_refs.generationStatus`，失败信息写入 `generationError`。
   - 成功图片原位替换占位卡，并以确定性的媒体 ID 写入原有相册；重复点击不会并发重复请求。
   - 编辑器中的待合成图片也使用同一占位卡样式，不会把内部 pending 标记当作破图地址显示。
   - 角色作者动态未来也复用同一渲染/生成入口；角色出镜照才允许按既有身份参考规则生成，普通场景不注入角色外貌。

2. 摇一摇陌生人
   - 首页新增“摇一摇”入口；当前阶段使用本地多样化模板生成临时档案，不产生 API 消耗。
   - 临时陌生人独立存入 `moments_temp_strangers` 与 `moments_profiles`，可长期保留最近遇到的人。
   - 临时聊天原文逐条存入 `moments_temp_transcripts`，可继续聊天；不创建正式角色、不进入正式记忆宫殿，
     也不会污染普通私聊。
   - 陌生人只能在用户打开设置并允许时查看用户最近十条公开动态；临时阶段不能点赞、评论或回复。
   - 点击“加好友”会创建正式 `CharacterProfile`，迁移临时聊天为一条角色记忆，并保留逐条迁移标记与索引，
     朋友圈资料同步切换为正式好友。

3. 事件账本与记忆索引
   - 用户发帖、点赞、评论、转发都会写入独立 `moments_event_ledger`，同时为有权角色写入
     `moments_memory_index`，保存稳定 sourceId/postId 和可见对象快照。
   - 删除动态时同步清理对应媒体引用、点赞评论、事件账本与直接派生的朋友圈记忆索引；不删除普通聊天正文。
   - 这些记录尚未接入角色上下文检索或记忆宫殿事件盒；阶段 4 已为必要事件增加独立 sync outbox，见下一节。

六、第四批第一段：朋友圈副 API、统一互动规划与 Worker（本段完成，第四批继续）
----------------------------------------------------------------------------

本轮仍只改朋友圈独立数据域和新增适配层，不改原版 AMSG Worker 的核心逻辑，也不恢复外卖模块。

1. 朋友圈副 API 设置
   - `apps/MomentsApp.tsx` 的“朋友圈设置”新增独立副 API 区域，可跟随主聊天 API、选择已有预设，或自定义 URL/Key/模型。
   - 支持“拉取模型”“测试连接”“保存副 API”；测试只请求 `/models`，不制造帖子或消耗聊天生成额度。
   - `utils/momentsApi.ts` 统一规范 OpenAI-compatible URL、鉴权、模型列表与错误提示；副 API 失败不会回滚用户帖子。

2. 一次规划、错峰执行和评论重排
   - 用户发布动态后，副 API 一次性返回首轮点赞/评论名单、评论正文、dueAt、threadVersion、幂等信息；最多 8 条评论，允许少于 8 条。
   - 未发生用户评论时，不按角色人数重复调用 API；到点由本地任务执行器落地点赞/评论。
   - 用户新增评论/回复后，仅取消未发送任务并调用一次统一重排，最多规划 3 条新回复；已经发出的互动不可改写。
   - `MomentsPendingJob` 保存 `payload/threadVersion/remoteTaskId`，按稳定任务 ID 去重，失败保留 `error` 供排查。

3. 角色自动发帖判断
   - 低/中/高发帖档位在副 API 已配置且自动行为开启时生效；模型根据人设、近期动态和当前时间判断是否“确实值得发”，不强行凑数。
   - 关闭/只看不发/没有副 API 时不发、不调用；睡眠时间由提示词约束不发。
   - 每个角色每天有本地检查幂等标记，避免刷新页面重复生成同一条日常动态。

4. 本地队列与离线同步
   - `utils/db.ts` 新增 pending jobs 与 sync outbox 读写；每 30 秒执行到期任务，重新打开朋友圈时继续执行。
   - `utils/momentsSync.ts` 将事件与任务分开同步到现有 AMSG Worker 的 `/moments/*` 路由；成功删除 outbox，失败保留并在设置显示错误，可手动重试。
   - Worker 只保存结构化事件/任务摘要，不接触朋友圈副 API Key；本地应用仍是生成与实际互动执行者。

5. 挂载到现有主动消息 2.0 Worker 的朋友圈路由
   - 路由源码：`worker/moments/src/index.ts`，由 fork 的 `worker/amsg/src/index.ts` 以 `/moments/*` wrapper 引入。
   - 正式部署 bundle：`worker/amsg/worker.bundle.js`（已把 AMSG 原有逻辑和朋友圈路由打在同一个 bundle）；
     `worker/moments/worker.bundle.js` 仅作独立预览/测试，不能拿它覆盖正式 AMSG Worker。
   - 建表脚本：`worker/moments/schema.sql`；正式运行时在已有 `DB` 中幂等创建 `moments_*` 表，不需要新建 D1。
   - 配置/部署说明：`worker/moments/README.md`。用户只需在已有 AMSG Worker Dashboard 的 Edit code 中替换
     `worker/amsg/worker.bundle.js` 并 Deploy，保留原来的 DB、Cron、AMSG_MASTER_KEY、VAPID、Durable Object
     和 `AMSG_SERVER_TOKEN`。
   - 路由：`GET /moments/health`、`POST /moments/sync`、`GET /moments/tasks`、`POST /moments/tasks/claim`、
     `POST /moments/tasks/complete`、`GET /moments/diagnostics`。
   - `AMSG_SERVER_TOKEN` 通过 `X-Client-Token` 同时保护 AMSG 和朋友圈路由；`MOMENTS_TOKEN` 仅为独立预览兼容。
     前端从“主动消息 2.0”全局配置读取 Worker URL、userId、serverToken，不再保存或填写第二套配置。
   - Worker 只负责朋友圈队列/同步、幂等、诊断和 stale running 任务回收，不替换 AMSG，不直接调用聊天模型，
     不在云端直接发聊天消息；原版 AMSG 核心处理和 scheduled 流程未改。

十、Worker 配置纠偏与源码核对（2026-09-01）
-----------------------------------------------

此前阶段 4 的初稿把朋友圈 Worker 写成了独立服务，并在朋友圈设置中增加独立 URL/令牌输入；这与用户
已经部署的主动消息 2.0 Worker 不一致。本次已按原版仓库与现有二改源码重新核对并纠正：

1. 上游核对
   - 当前 `upstream/master`（`qegj567-cloud/SullyOS`，同步检查到 `2b6af21f`）的 `worker/amsg`
     没有朋友圈代码、`worker/moments` 目录或 `/moments` 路由。
   - 上游仓库只读；本次没有向原版提交或覆盖任何代码。

2. 二改源码边界
   - `worker/amsg/src/index.ts` 仅新增一个 fork-only 路由分流：路径为 `/moments` 或 `/moments/*`
     时调用 `worker/moments/src/index.ts`；其它 fetch 路径、原版 AMSG handler 和 `scheduled()` 主流程
     保持原有顺序。朋友圈的 stale 任务清理由同一每分钟 Cron 以隔离 try/catch 执行，失败不阻断 AMSG。
   - `worker/moments/src/index.ts` 只使用同一个 `DB` 创建 `moments_*` 表；鉴权优先兼容独立预览令牌，
     正式挂载时复用 `AMSG_SERVER_TOKEN`，请求头统一支持 `X-Client-Token`。
   - `utils/momentsSync.ts` 的同步地址已固定为 `${现有Worker地址}/moments/sync`，拉取任务使用
     `/moments/tasks`，不再请求根路径 `/sync`。
   - `apps/MomentsApp.tsx` 通过 `ActiveMsgStore.getGlobalConfig()` 读取主动消息 2.0 已保存的
     `workerUrl/userId/serverToken`；朋友圈设置改为只读状态和“重新读取配置/立即重试同步”，不保存第二套凭据。
     `MomentsSettings.worker` 字段仅为旧备份兼容保留，不再作为运行时来源。

3. 正式部署结论
