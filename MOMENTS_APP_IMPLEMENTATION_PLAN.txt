一、目标与不可变边界
----------------------

1. 在 Duck 栏中以全新的“朋友圈 App”替换当前“小红书”入口与对应 App 页面。
2. 视觉与交互以现实微信朋友圈为目标：封面、头像、昵称、纵向动态流、九宫格、全文、点赞评论、
   评论回复、消息页、个人时间线、置顶与隐私选择。使用 SullyOS 自有代码/资源，不连接微信服务。
3. 系统设置中的“实时感知小红书”完全保留，不改代码、不改数据、不改入口。
4. 朋友圈是独立模块，不把帖子、点赞、评论自动变成聊天 HTML 卡片；只有用户主动“转发给角色”时，
   才在该私聊显示一张专用、紧凑且美观的朋友圈转发 HTML 卡。
5. 朋友圈、角色记忆、主动消息 2.0、聊天生图、相册之间必须采用结构化事件与稳定 ID 联动，
   不依赖关键词猜测，也不得因重试/刷新产生重复动态、重复评论或重复主动消息。

二、v1 可见功能合同
--------------------

1. 用户朋友圈
- 用户可发布文字 + 最多九张图片的动态；支持从小手机相册选图、上传本地图片、删除已选图片。
- 用户可改封面、查看自己的相册时间线、删除自己的帖子。
- 删除带图帖子时询问：“只删除朋友圈动态”或“同时从小手机相册删除图片”。
  只有该图片未被聊天、其他帖子、相册项目等其他记录引用时，才允许真正删资产。
- 用户发布时选择隐私：公开给好友、部分可见、不给谁看、仅自己可见等微信式选项。

2. 角色朋友圈
- 已添加的正式角色可发文字帖、文字照片占位帖与已生成图片帖，可拥有封面、个人时间线与置顶动态。
- 点击角色头像可进入该角色自己的朋友圈时间线。
- 角色只在角色人设、日程、情绪和当前聊天共同判断“确实值得记录/分享”时发帖；不能每次聊天都发。
- 每角色设置分为两组：
  发帖频率：关闭 / 低 / 中 / 高 / 只看不发；
  互动方式：正常互动 / 只点赞不评论 / 不自动互动。
- 频率默认语义：低约每周 2–4 条；中约每天 1 条；高约每天 2–4 条。实际时刻遵守日程、性格、去重；
  日程睡觉时不自主发帖。用户正在与角色活跃聊天且内容值得分享时，可例外发帖。
- 角色按人设可对用户设置的分组决定低调、公开或屏蔽其他角色；权限必须结构化保存。

3. NPC 与摇一摇
- 角色人设/上下文中有明确姓名或稳定身份关系的 NPC，可作为精简朋友圈主体发帖、点赞、评论；
  只保留名字、身份、头像兜底、帖子与互动，不预建复杂资料页、完整角色档案或临时私聊。
- 明确 NPC 的朋友圈提供“添加好友”。添加时复用“协同工作 → 角色卡制作”的同一套 `character-card` 作品协议，
  并以来源主角色核心人设、用户/主角色/NPC 的身份说明，以及主角色与该 NPC 最相关的五条记忆为制卡事实；
  解析与落库同样复用协同工作的原生 `name / description / systemPrompt / worldview` 映射，之后成为正式角色，
  才进入正常聊天与记忆系统。
- 摇一摇生成临时陌生人：候选角色约 80% 为有吸引力的帅哥/美女，仍允许丰富多变的反差人物。
  首次页面显示头像、昵称、简介、封面、可见的最近十条朋友圈及“发消息 / 添加好友”。
- 摇一摇陌生人有可长期保留的临时档案与临时私聊；不进入正式角色列表、聊天主记录或记忆宫殿。
  用户添加好友后才执行一次明确迁移，并保留临时原文可查看。

三、可见性、隐私与转发合同
----------------------------

1. 分组
- 朋友圈的“部分可见 / 不给谁看”复用现有角色分组为基础，并允许新建仅供朋友圈隐私使用的补充分组。
- 朋友圈补充分组不会影响其他 App 的角色筛选/分组逻辑。
- 每条帖子创建时冻结权限版本与实际可见对象快照；后续改分组不会泄露旧动态。

2. 陌生人最近十条
- 提供简单总开关“陌生人可看最近十条朋友圈”：开 / 关。
- 开启后，摇一摇且尚未加好友的陌生人只能浏览符合该帖权限的最近十条，不得越过单帖屏蔽或私密范围。
- 陌生人不能点赞、评论、回复评论或打开原帖互动区；可在临时私聊自然提起看见的动态。

3. 手动转发
- 情形 A：接收角色原本被该帖屏蔽。转发仅提供定向动态快照，可在私聊讨论，不能打开原帖、点赞、评论；
  原帖隐私不改变。
- 情形 B：接收角色原本有可见权，仅因角色多且尚未刷到。转发提供动态快照并记为实际送达/已阅；
  角色可以打开原帖、点赞、评论、回复评论。
- 定向转发带原帖 sourceId；撤回/删帖后，未发送互动与直接派生的事件可级联回收。

四、互动合同与调用量控制
--------------------------

1. 谁可以互动
- 互动候选仅来自对该帖有可见权的已添加好友角色与可见 NPC；被屏蔽者、无可见权者、未加好友的
  摇一摇陌生人不参与。
- 可见不等于已看见：发帖者、点赞者、评论者、被回复者必定记录事件；其他角色只有实际浏览、被转发、
  被自动互动选中或被提及时才获得“已阅/参与”事件和相关记忆。

2. 自动互动比例
- 已添加好友角色数 <= 3：全部角色都会评论。
- <= 5：约 80% 会点赞或评论。
- <= 10：约 50%–80% 会点赞或评论。
- > 10：最多 50% 会点赞或评论。
- 随机 NPC 不计入上述人数分档，只可作为补充参与者。
- 每一帖固定参与名单和幂等键；刷新、重试、重新打开不重新随机，不产生第二批互动。

3. 自动评论防爆
- 首轮自动评论最多 8 条，可少于 8 条，绝不为凑数强行评论。
- 用户每次在评论区新增评论/回复后，新增自动回复最多 3 条，不重新开启一轮 8 条首轮评论。
- 同一条帖子生命周期内，随机 NPC 自动评论总数最多 3 条（含首轮与后续回复）。
- 点赞不计入评论上限，但仍受可见权、互动比例、去重和后续单日互动限制。
- 互动按角色日程与性格生活化错峰出现，不整齐刷屏；精确延迟窗口作为实现参数独立配置。

4. API 调用模型：先完整规划，用户介入时统一重排
- 帖子发布后，用朋友圈副 API 进行一次“互动规划”批量调用，输出该帖所有自动互动的参与名单、
  点赞/评论类型、完整评论正文、时间顺序、推送时间、threadVersion 和幂等键。
- 用户没有介入评论区时，自动互动只消耗这一次规划调用；到点由本地/Worker 直接投递预写内容，
  不按角色数量再调用 API。
- 用户新增评论/回复评论时，进行一次“评论区回应与统一重排”调用：
  a) 决定被直接回复者及少量合适旁观者是否回应，并生成新增回复；
  b) 对所有尚未发出的评论按最新评论区和私聊近况重写正文、调整顺序/时间、改为点赞或取消；
  c) 已发送互动绝不改写、不重抽；所有未发任务以新 threadVersion 替换旧版本。
- 用户快速连续评论可短暂合并为一次重排；用户明确点名/追问某角色时立即发起本轮调用。
- 这使调用量约为“帖子一轮 + 用户实际介入评论区的轮数”，而不是“可见好友人数”或“页面刷新次数”。

五、图片、相册与生图合同
--------------------------

1. 朋友圈图片沿用聊天生图的延迟合成体验：角色先发布文字照片占位，用户点击才调用生图模型。
2. 不读取聊天页面生图开关；只要“其他 API”中存在可用生图配置即可使用。
3. 朋友圈设置只选择/配置用于文本社交内容的副 API；图片仍走现有生图 API 体系。
4. 成功生成或发出的朋友圈图片默认进入小手机相册，可查看、保存；同一照片重生成时按动态/图片 ID
   保留最新版本，并避免无谓重复资产。
5. 生图失败必须显示可查错误；动态保留文字占位，可重试，不影响帖子、互动或聊天。

六、记忆、上下文与删除合同
----------------------------

1. 原始朋友圈事件账本
- 每条帖子、图片、点赞、评论、回复、转发、已阅、删除均为稳定事件，带 eventId、postId、作者、参与者、
  时间戳、递增序号、可见性快照、来源类型与删除状态。
- 这是事实源头，不需等待记忆宫殿，确保帖子刚发生时角色已能在近期生活线里理解它。

2. 角色生活线
- 角色回复私聊、发帖、评论时，后台合并“正常私聊近况 + 自己有权看见且实际看过/参与的朋友圈事件”，
  按时间组成角色视角生活线；UI 不自动显示朋友圈卡片。
- 只注入当前角色、当前关系、当前话题或最近时间相关的少量事件，避免上下文爆炸。
- 私聊在 A 与用户之间发生，B 不会凭空知道；只有可见朋友圈、定向转发或用户直接对 B 所说的内容，
  才能进入 B 的生活线。

3. 记忆宫殿
- 记忆宫殿将一条帖子及其互动聚合为“朋友圈事件盒”，保留子事件 ID；不把每个点赞拆成重复长期节点。
- 按角色视角归档：发帖者、评论者、浏览者分别保存各自经历；所有原始事件仍留在账本中可追溯。
- 记忆节点/索引必须带 `sourceType='moments'` 与 postId/commentId/sourceId，支持精确级联删除。

4. 临时陌生人迁移
- 临时私聊原文永不因压缩而丢失，但单次模型调用仅带固定人设 + 最近一段对话（受模型上下文上限约束）。
- 添加好友时，明确创建正式角色、保留原文档案，并把临时聊天及该陌生人实际看见/参与的朋友圈事件作为
  可追溯迁移批次写入正式记忆库和记忆宫殿。

5. 删除
- 删帖/删评论/撤回转发按 postId 或 sourceId 级联撤销原始事件、图片关联、已阅、未发任务、Worker 关系事件、
  直接派生记忆索引与记忆宫殿事件盒。
- 已经独立存在的普通私聊文本不伪造改写；但其原始朋友圈来源不再被后续上下文召回。

七、离线 Worker、关系层与醋意合同
------------------------------------

1. 朋友圈 → Worker/D1 同步
- 为支持用户关闭小手机后的自主发帖、错峰互动和角色主动联系，本地朋友圈要把经过可见性过滤的必要事件
  同步给 Worker/D1。无权角色不接收帖子内容或存在提示。
- Worker/D1 只保留关系判断和计划投递所需的 eventId、postId/commentId、时间、参与者、可见对象、必要摘要、
  权限版本、threadVersion、任务状态与幂等信息；完整 UI 数据仍在本地。
- 同步失败必须可重试、有 pending/失败原因诊断；到点任务投递前再次校验帖子未删、权限未失效、对象未拉黑。

2. 醋意
- 醋意为每角色独立 0–100 状态，继续在关系心声卡中展示。
- 增长信号：角色实际看见其他暧昧朋友圈、实际看见用户和他人在评论区亲密互动、用户在与该角色的私聊中
  深情夸其他角色/二次元人偶/演员/偶像，以及符合人设的比较、冷落、排他信号。
- 每次增减按角色占有欲/克制程度、关系、好感、近期互动、事件强度和重复性评估，保留 eventId、原因与变动。
- 单纯回复不降醋意；可识别的安抚、解释、偏爱、和好才明显回落。敷衍/回避/继续刺激可不降或上涨。
- 删除来源事件时回收其尚未被后续独立事实覆盖的影响；随后真实发生的普通私聊不被伪造删除。

3. 醋意阈值 80 与强制主动联系
- 醋意 >= 80 时立即创建 `jealousy-critical` 高优先级原版 AMSG 联系机会，不等待思念阈值、普通联系时间、
  常规最短间隔或普通每日次数。
- 提供默认开启的独立开关“醋意强制联系”：开启时也越过免打扰和用户关闭常规主动消息的状态；关闭时仍计算、
  同步、展示和诊断醋意，但不强制投递。
- 同一角色同一轮醋意爆发必须有 critical pending/已触发锁。高醋意强势接管一次对话，不允许每分钟重复创建任务。
- 对浏览器刚产生的信号立即评估/排任务；离线自主发帖产生的信号由 Worker 生成时评估。实际抵达仍受网络、
  原版任务投递与模型可用性影响。

八、朋友圈副 API 与设置合同
------------------------------

1. 朋友圈设置提供独立副 API：默认跟随主聊天 API；可选择系统既有 API 预设；可自行填写 URL、Key、模型。
2. 必须支持拉取模型、模型选择、测试连接、保存，并以统一 API 适配器处理 OpenAI 兼容模型。
3. 朋友圈副 API 用于角色发帖、互动规划/重排、摇一摇人设与必要的文本处理；图片继续使用生图 API。
4. 配置、帖子、互动、权限、临时陌生人、临时聊天、媒体引用、任务状态、记忆索引都必须纳入完整备份与恢复。
   备份格式升级必须向后兼容，不得重演 formatVersion 导入失败或图片丢失的问题。

九、数据模型与安全回退设计
--------------------------

1. 独立数据域（不写入 phoneState、不污染聊天表）
- moments_profiles、moments_posts、moments_media_refs、moments_visibility_snapshots；
- moments_reactions、moments_comments、moments_seen_receipts、moments_shares；
- moments_temp_strangers、moments_temp_transcripts、moments_event_ledger；
- moments_settings、moments_pending_jobs、moments_sync_outbox、moments_memory_index。

2. Worker/D1 独立数据域
- moments_relationship_events、moments_tasks、moments_sync_receipts、moments_diagnostics；
- 所有表和任务携带 userId、charId、eventId、权限版本、幂等键；不与原版 AMSG 核心表混写。

3. 功能开关与回退
- Dock 入口替换为朋友圈，但保留可恢复的旧入口映射/迁移策略；不删除设置里的实时感知小红书。
- 朋友圈独立总开关、自动互动开关、离线同步开关、醋意强制联系开关均可单独关闭。
- 每阶段只新增可识别的字段/表；发生故障时关闭阶段开关即可停止新行为，既有数据不丢、不需整仓回滚。
- 每次发布前记录源文件、数据迁移、测试结果、Pages 提交、是否需要 Worker 部署；不可把网页发布误称为 Worker 已更新。

十五、阶段 5 实施修订（2026-09-01，本地已完成，待网页发布/重新部署 Worker）
------------------------------------------------------------------------

1. 结构化醋意事实
   - 每个角色独立保存 0–100 醋意与最近 128 个稳定 eventId。事实只含来源类型、有限强度、原因摘要和时间；
     不将帖子正文、评论全文或私聊原文上传到 Worker。
   - 朋友圈只在角色实际刷到、被选中互动、手动转发送达或被用户直接回复时，才允许为该角色创建事件；单纯拥有
     可见权绝不涨醋意。用户私聊中明确偏爱其他已添加角色、比较/冷落、或明确安抚同样通过消息 ID 去重。
   - 普通回复不降醋意；明确安抚、解释、偏爱才回落。跌到 70 以下才重新允许未来的一轮强制接管。

2. 阈值与原版 AMSG 接管
   - 醋意 >=80 且“醋意强制联系”开启时，立即建立一条 `jealousy-critical` 高优先级原版 AMSG 联系机会；
     它越过普通思念阈值、每日次数、最短间隔、免打扰和常规关系层开关，但仍通过原版 fire-time 生成与送达。
   - 同一轮有独立 `criticalPendingTaskUuid` 和 latch；成功建立后不会每分钟重复创建。创建失败保留原因并每五分钟
     有限重试；真正送达后也不会假装“已被安抚”。
   - 关闭强制开关后仍照常计算、同步、展示和诊断醋意，只是不创建 critical 任务；重新开启会同步给已有角色状态。

3. 第四批补齐项
   - 角色自主发帖尊重副 API 返回的发帖时间（保留最小错峰安全窗），并允许按角色人设冻结公开/对特定角色低调
     的 visibility snapshot；之后改分组/人设不会改写旧帖权限。
   - 朋友圈记忆索引只写给实际参与、实际 seen 或手动转发送达的角色，删除了“所有可见角色都被写成已记住”的旧路径。
