================================================

用途
----

本文件是朋友圈 App 后续维护的唯一审计入口。继续开发、排错、同步原版或发布前，优先阅读本文件，

备份路径、AMSG 合并 Worker、构建与测试”的交叉核对结果。

本次范围与结论
--------------

1. 本次只审计、构建和静态核对；没有修改业务源码、没有发布网页、没有部署 Worker。
   为了验证产物，执行过本地构建，因此 worker bundle 按现有源码重新生成；不代表线上部署已被本机验证。

2. 朋友圈不是“空壳”：入口、主界面、基础本地数据、基础发帖/评论/隐私、聊天图片占位卡、
   本地互动任务队列，以及合并到 AMSG Worker 的 /moments 路由均真实存在。

3. 但不能把当前状态称为“实施方案阶段 1–4 已完整完成”。其中存在备份遗漏、删帖安全、
   Worker 任务认领、NPC/陌生人、角色发帖规则、互动重排、记忆宫殿接入等未闭环或未实现内容。
   以后不得仅根据“有表、有 type、有说明文档”就认定功能完成。

4. 用户已说明 Worker 已更新。代码层面已确认正式部署产物应为 worker/amsg/worker.bundle.js，
   且该 bundle 包含朋友圈路由和定时调用。由于本机对 workers.dev 的外部 curl 连接被重置，
   本次无法从本环境独立证明线上 Worker 已运行；此结论不否定用户的部署结果。


一、已实际存在且已通过源码/构建核对的基础能力
----------------------------------------------

1. App 入口
   - Duck 栏原“小红书”槽位已显示为“朋友圈”。
   - PhoneShell 可懒加载 apps/MomentsApp.tsx；预加载配置也已加入。
   - 旧 SocialApp / social_posts 仍保留，没有被直接挪用为朋友圈数据。

2. IndexedDB 数据层
   - utils/db.ts 的 v72 已创建 16 个 moments_* 数据表。
   - DB.exportFullData() / DB.importFullData() 这一组直接数据库导入导出函数，已经包含 momentsData。
   - 注意：这不等于系统设置里的真实 ZIP 完整备份已包含朋友圈，详见“最高优先级问题”。

3. 前端基础体验

   - 用户发帖有公开、部分可见、不让谁看、私密的基础选择；已选受众会冻存在 post.visibility 内。

   - AMSG 的 scheduled 入口会隔离调用 momentsWorker.scheduled()；朋友圈异常不会直接打断原版 AMSG。
   - 正式发布 bundle 是 worker/amsg/worker.bundle.js；worker/moments/worker.bundle.js 只是单独预览产物，
     不是应部署的新 Worker。
   - 本地 pnpm run build 通过，两个 bundle 的 node 语法检查通过。


二、必须优先修复：数据安全与可恢复性
----------------------------------------

P0-1 系统完整备份漏掉所有朋友圈数据
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

现状：
  - 设置中的导出入口调用 OSContext.exportSystem()，不是 DB.exportFullData()。
  - exportSystem 的 allStores 列表没有任何 moments_* 表；写入 backupData 的映射分支也没有 momentsData。
  - 因此用户从设置导出的正常 ZIP/完整备份不会保存动态、朋友圈人物、评论、反应、设置、任务、
    outbox、记忆索引等。图库文件或许在，但朋友圈记录不会再指向它们。

风险：
  - 一旦更换浏览器、清站点数据或恢复备份，朋友圈数据可能整体消失。

修复验收：
  - exportSystem 的 allStores 与字段映射加入所有 16 个 moments_* 表；导入也做格式兼容与事务级回滚。
  - 新建“发布文字/图片、评论、互动任务、媒体引用”的测试数据，导出后清库再导入，逐项核验。

源码定位：
  - context/OSContext.tsx：allStores 约 3900 行；备份映射 switch 约 4473 行。
  - utils/db.ts：直接导出约 3587 行、直接导入约 4091 行（这两处已有 momentsData）。


P0-2 删帖会无引用检查地删除图库图片，且没有完整级联
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

现状：
  - MomentsApp.confirmDelete() 对帖子中的每个 galleryImageId 直接 DB.deleteGalleryImage()。
  - 未查询图片是否仍被聊天、另一条动态、相册别名或其他功能引用。
  - 删除没有写出“删除事件/tombstone”，也没有同步取消远端任务。

风险：
  - 用户确认“同时删除图片”时，可能误删仍在聊天或其他动态中使用的真实图片。
  - 已删除动态关联的远端任务、outbox、分享记录、已读记录与后续互动可能重新出现或继续执行。

修复验收：
  - 对每张图库图片做全库引用检查，仅在零引用时删除；保留时明确提示用户。
  - 删除应同时清理/取消：评论、反应、可见性快照、分享、已读、待执行任务、outbox、远端任务、
    事件索引及未来的记忆宫殿事件盒；并写可同步 tombstone。

源码定位：
  - apps/MomentsApp.tsx：confirmDelete 约 556 行。


P0-3 可见性快照表的主键与类型不一致
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

现状：
  - moments_visibility_snapshots 表的 keyPath 是 id。
  - MomentsVisibilitySnapshot 类型没有 id；当前 App 也没有真正写入该表。
  - 基础展示暂时依赖嵌在 post.visibility 里的冻结 audienceIds，所以尚未立即报错。

风险：
  - 一旦真实写入或导入独立可见性快照，IndexedDB put 可能因缺主键而失败。

修复验收：
  - 类型与落库对象添加稳定 id，或将 store keyPath 改为真实已有字段；为导入增加兼容转换。

源码定位：
  - utils/db.ts：约 390 行。
  - types.ts：MomentsVisibilitySnapshot 约 3750 行。


三、实施方案中尚未真正完成或只完成骨架的功能
------------------------------------------------

1. NPC 与人设中明确 NPC
   - 类型/API 可表示 npc，但 loadData 仅把正式 characters 同步为朋友。
   - 没有从角色人设或上下文提取明确 NPC；没有 NPC 头像/封面、动态、评论、资料页或加好友入口。
   - 计划要求的“明确身份 NPC 有朋友圈、可添加为好友、评论可形成互动记忆”尚未实现。

2. 摇一摇陌生人
   - 已有 80% 帅哥美女的文字模板和一个本地抽取界面。
   - 但没有真实头像/封面与个人动态；陌生人只能看到用户公开的最近十条。
   - 临时聊天是三句固定回复，未使用配置的朋友圈副 API，也没有上下文/可见动态支撑。
   - 添加好友后只建了泛化 character 与一条摘要 MemoryFragment，未把临时聊天、看过的动态、
     已发生互动迁入正式、可检索的角色记忆链。

3. 角色主动发帖
   - 当前只在 MomentsApp 打开并挂载时本地检查；不具备关闭小手机后主动发帖能力。
   - 每角色每天最多触发一轮检查，不符合低/中/高的 2–4 次/周、每天 1 次、每天 2–4 次的分布设想。
   - 未读取日程或当前私聊上下文；睡眠判断只是提示词文字，不是实际日程约束。
   - API 返回的 dueAt 没有被延后执行，帖子会立即创建。
   - 角色动态固定公开；角色无法按性格选择分组、低调恋爱、部分可见、置顶/删帖。
   - 角色发图查找 character 时用的是 moments:character:<id> 与原角色 id 直接比较，取不到对应角色，
     会退回用户占位参考，无法稳定注入正确的角色外貌参考。

4. 每角色互动档位与朋友圈专属分组
   - 计划中的“正常互动 / 只点赞不评论 / 不自动互动”没有数据字段、设置 UI 或执行逻辑。
   - 仅有角色发帖频率字段，且 UI 不完整。
   - 当前只复用已有 characterGroups 并临时点选个人，尚无可单独保存的朋友圈补充分组。

5. 自动点赞评论与重排
   - 互动规划 API 提示词未真正落实好友数量对应的 100% / 80% / 50–80% / ≤50% 概率规则，
     也没有每日互动上限、NPC 至多三条等硬约束。
   - 用户评论后会取消 pending job 再新规划，但没有排除已发过互动的角色；同一角色可能在 v1、v2 中重复点赞/评论。
   - 没有对用户连续回复的合并/防抖，因此可能频繁重排并多耗 API。
   - 消息页只是每次由全部互动推导，缺少已读/清除状态；红点并不是真正可消失的未读系统。
   - 用户作为动态作者时，不能长按删除别人留在自己动态下的评论，只能删除自己写的评论。

6. 可见性、刷到与已读回执
   - 冻结 audienceIds 的基础隐私逻辑存在；但 planned 的 eligible / seen / selected_for_interaction 回执没有实现。
   - Worker 同步时 receipts 始终为空；记忆索引对“能看到的人”写得过宽，无法说明谁真的刷到、谁被抽中互动。
   - 手动转发快照卡区分可见/被屏蔽有基础实现；“未被屏蔽但本轮没刷到”的受众逻辑尚未完整闭环。

7. 记忆、时间线与记忆宫殿
   - moments_memory_index 表和简单 ledger 存在，但没有聊天上下文读取方，也没有 Memory Palace 的事件盒。
   - ledger 缺少计划要求的 sequence、sourceType、摘要与可靠删除状态；没有 sourceType=moments 的统一事件流。
   - 因此朋友圈和私聊尚不能按真实发生顺序统一检索、压缩、删除或迁移。
   - 工作记录本身曾注明“尚未接入角色上下文检索或记忆宫殿事件盒”，应以源码现状为准。

8. 生图细节
   - 同一段文字的重新 roll、“只保留最新图”的版本淘汰机制尚未完整实现。
   - 合成失败只给“点击重试”和短暂 Toast，缺少可长期查看的失败详情。
   - 图片成功写图库后，当前页面的 gallery React state 未刷新，选择器可能要刷新页面后才显示新图。

9. 设置项的空开关
   - MomentsSettings 中 offlineSyncEnabled、jealousyForceEnabled 目前只有类型和默认值，没有真正 UI/执行门控。
   - 全局 enabled 也没有明确禁止发帖/同步的完整门控。
   - Worker 配置存在时仍可能同步，和 offlineSyncEnabled 默认 false 的语义冲突。
   - 醋意强制主动消息本来属于未开始的阶段五，当前不能表述为已具备。


四、Worker / 离线任务的真实状态与问题
--------------------------------------

已确认存在：
  - /moments/sync、/moments/pull、/moments/claim、/moments/complete、/moments/diagnostics 端点。
  - scheduled 会处理 stale running 任务的回收，且不直接干扰原 AMSG 主流程。

尚未闭环：
  1. Worker 不会生成或派发内容，只存储任务并回收过期 running 任务。
  2. 前端只会 sync/pull；没有调用 claim/complete。取回任务后直接在本地执行，多标签页/多设备可能重复执行。
  3. App 仅在 MomentsApp 已打开时每 30 秒执行本地任务。小手机关闭时任务不会自动发出；
     其他端新入队的任务也不会被持续拉取。
  4. Worker 每次最多接收 200 条 event/task；前端任一 sync 成功后却删除全部 outbox，超过 200 条会丢失。
  5. 远端 task upsert 可被旧本地 pending 状态覆盖掉 running/done/cancelled 状态。
  6. 动态删除没有远端取消/删除协定，旧任务可继续回来。
  7. Worker 的 token 选择优先 MOMENTS_TOKEN，再退回 AMSG_SERVER_TOKEN。正式方案要求共用 AMSG token；
     若 Cloudflare 中遗留 MOMENTS_TOKEN 且与前端 AMSG token 不同，会造成 401。需要明确只保留一致的凭据策略。
  8. diagnostics 端点虽有，前端没有调用，设置页不能显示真实远端任务/报错。
  9. Worker 原样保存完整 entry payload，可能携带整条动态/评论，不符合“只存必要摘要”的最小化目标。

第二批修复记录（2026-09-01，本地已验证，待发布/重新部署 Worker）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

以下问题已从上述“尚未闭环”列表中移除或降级：

1. 原子任务认领与完成回执
   - 前端在执行到期任务前调用 `/moments/tasks/claim`；未认领成功时不执行，避免多设备重复落地。
   - 完成或失败后调用 `/moments/tasks/complete`；网络错误时保留 pending 并等待下一轮，不绕过 Worker 强行执行。
   - pull 不再把远端 running 伪装回本地 pending；本地终态不会被较旧的远端状态覆盖。

2. 分批确认与单调任务状态
   - 同步每类最多 200 条，Worker 返回明确的 acceptedEventIds / acceptedTaskIds；前端只删除这些已确认 outbox。
   - Worker upsert 不允许旧 pending 覆盖 running，也不允许非取消状态覆盖 done/cancelled。
   - 已删帖 tombstone 继续优先取消该帖 pending/running 任务。

3. 互动规划防爆
   - 好友数量规则先在本地筛选，再交给副 API：≤3 全入选，≤5 约 80%，≤10 约 65%，>10 50%。
   - 重排前读取已发点赞/评论并排除对应角色；旧 pending 才取消；连续用户评论在 700ms 内合并为一次重排。
   - 首轮仍最多 8 条评论，重排最多 3 条；不会按角色逐个调用 API。

4. 消息与管理体验
   - 消息红点由 lastInboxReadAt 持久化，用户打开消息页才标为已读。
   - 动态作者可长按删除自己动态下的任意评论；评论作者仍可删除自己的评论。
   - 设置增加“读取 Worker 任务诊断”，显示待执行/执行中/完成/失败数与最近诊断，不显示密钥。

仍未完成：真正关闭小手机后的内容生成/派发、全量远端已读回执、NPC、角色生活线、记忆宫殿、
以及 Worker payload 最小化，仍按原先第三、四批处理。

相关定位：
  - utils/momentsSync.ts：仅 sync/pull，约 19 行。
  - worker/moments/src/index.ts：token 约 72 行，200 条截断/upsert 约 85 行，claim/complete 约 127 行，
    scheduled stale 回收约 173 行。
  - worker/amsg/src/index.ts：路由与 scheduled 合并约 109、3064、3175 行。
