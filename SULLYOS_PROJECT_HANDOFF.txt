6. 云端即时对话：可停止生成（2026-08-31）
-------------------------------------------

适用范围：角色回复正通过主动消息云端链路生成、聊天中出现 pending 气泡时。

- pending 气泡会显示“云端生成中”和“停止生成”入口；用户可随时中止这一次等待；
- 点击后调用既有的 `cancel-message` 任务取消接口。接口确认取消（含任务已被消费的正常情形）后，
  本地立即结束生成态并清除暂存通知；
- 已取消任务的 UUID 会在网页端保留 24 小时。即使云端模型已经算完、随后补发推送或 outbox 回填，
  聊天运行层也会拦截并确认该迟到回复，绝不再写入聊天记录；
- 若取消请求本身因网络或鉴权失败，保留生成态并显示错误，不假装已经取消，避免把可能即将成功的回复吞掉；
- 这是前端/网页端补丁，复用现有 Worker 接口，**不需要重新部署 Cloudflare Worker**。它不能承诺
  让上游模型的物理计算瞬间停止，但能让用户立刻脱离等待，并确保迟到结果不再显示；
- 仅作用于这条云端 pending 回复，不改变浏览器本地直连生成逻辑，也不影响原版主动消息任务逻辑。
- 2026-09-01 已记录一次只读排查：设备到 `workers.dev` 的入口链路可在 TLS/响应头之前被重置；请求进入
  Worker 后，即时 fire 又允许单轮最多 10 分钟并按 2/4/6 分钟退避重试，因此“长时间生成后自行恢复”

四、每次改代码后的发布铁则
----------------------------

用户明确要求：每次真实修改后，必须更新 GitHub Pages，不能只改本地后口头说完成。

标准流程：
1. 检查 git status 与 git diff --check，避免碰用户未跟踪资料。
2. 读取目标远端文件的当前 sha，确认不会覆盖用户/上游的新改动。
3. 只发布本次涉及的文件到 origin/master；本机 Git 历史与远端不同步时，优先使用 gh Contents API
   精确 PUT，不能直接推送整个工作树。
4. 推送/PUT 会触发 GitHub Actions 工作流“Deploy to GitHub Pages”；不要为了同一批改动重复手动
   触发多个部署。
5. 等待并确认 build 和 deploy 均为 success。
6. 最后才提供：
   https://mobufei0818-dot.github.io/SullyOS/?v=<最新远端短 SHA>

常用命令（执行前要确认当前目录和远端）：

检查远端 master：
  /opt/homebrew/bin/gh api repos/mobufei0818-dot/SullyOS/commits/master --jq '.sha'

查看最新部署：
  /opt/homebrew/bin/gh run list --repo mobufei0818-dot/SullyOS --workflow 'Deploy to GitHub Pages' --limit 1

等待部署：
  /opt/homebrew/bin/gh run watch <run-id> --repo mobufei0818-dot/SullyOS --exit-status

GitHub 网络偶尔会使普通 git push 卡住。已验证可用的发布方式：
- 定向小改动：用 gh Contents API 逐文件 PUT；更新前必须读取该远端文件的 sha，避免覆盖他人；
- 大型上游合并：先在独立同步分支完成并核对，再谨慎推送。若默认 HTTP/2 卡住，可用：
  git -c http.version=HTTP/1.1 push --progress origin <local-branch>:master

不要因为网络慢使用 force push；不要使用 gh repo sync --force；两者都可能毁掉二改历史。


五、同步原版的正确流程
------------------------

用户会说：
- “原版更新了，帮我同步”；
- “检查原版更新并同步二改”；
- “帮我 fork 一下”（此处通常指把原版更新合入其已有 fork，并非重新创建新 fork）。

正确流程：
1. 只读对比 origin/master 与 upstream/master，确认上游领先多少、最新提交内容及影响范围。
2. 不可直接强制同步或覆盖用户 fork；用户 fork 含外卖、生图、备份修复。
3. 基于 origin/master 新建临时同步分支，例如：
   git fetch origin master
   git fetch upstream master
   git switch -c codex/sync-upstream-YYYYMMDD origin/master
   git merge --no-commit --no-ff upstream/master
4. 逐一解决冲突：原则是“保留用户二改 + 接入上游新逻辑”，不能无脑选 ours/theirs。
5. 对二改关键交叉点重点复查：
   - apps/Chat.tsx
   - apps/Settings.tsx
   - apps/Character.tsx
   - components/chat/ChatModals.tsx
   - components/chat/MessageItem.tsx
   - context/OSContext.tsx
   - types.ts
   - utils/backupFormat.ts
   - utils/blobRef.ts
   - utils/safeApi.ts
   - utils/context.ts
   - utils/activeMsgClient.ts / utils/amsg2Tasks.ts
   - utils/imageGeneration.ts / utils/visionApi.ts
6. 完成 merge commit 后推送 origin/master。
7. 必须让 GitHub Pages CI 构建并部署成功；如失败，读取日志后修复，不要让用户使用坏链接。

同步前建议提醒用户自行导出完整备份；代码同步通常不清用户浏览器数据，但备份是安全网。


六、用户数据与安全边界
------------------------

- SullyOS 主要是 local-first：聊天、角色、API 设置、主题等存浏览器 IndexedDB/localStorage。
- 发布网页新版本不会主动清除用户数据。
- 导入备份、清除浏览器站点数据、重置系统才可能改变本地数据；执行前必须谨慎。
- API Key、NovelAI Token、高德 Key、Cloudflare 权限、GitHub Token 不得写入源码、日志或工作记录。
- GitHub Pages 是纯前端：任何直接填入前端的 Key 都会存在用户浏览器中，不能当作服务器密钥。
- 高德等敏感服务要配域名白名单、额度限制；需要真正隐藏密钥时再使用 Cloudflare Worker secret。
